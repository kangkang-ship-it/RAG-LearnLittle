## 一、用户隔离分析

### 1.1 当前已正确实现的隔离措施 ✅

| 层面 | 隔离机制 | 实现位置 |
|------|----------|----------|
| API 认证 | JWT Bearer Token + 黑名单 + 设备会话管理 | `app/utils/auth_utils.py` |
| 数据库查询 | 所有 SQL 查询带 `user_id` 过滤条件 | `app/models/`、各 Service |
| 向量检索 | ChromaDB `where={"user_id": user_id}` 元数据过滤 | `app/rag/vector_store.py` |
| 笔记操作 | CRUD 全部校验 `Note.user_id == user_id` 所有权 | `app/services/note_service.py` |
| 聊天会话 | 会话归属校验 `get_session(db, session_id, user_id)` | `app/services/chat_service.py` |
| 回顾记录 | 查询和标记均过滤 `ReviewRecord.user_id == user_id` | `app/services/review_service.py` |
| Agent 工具 | 每个工具通过闭包注入 `user_id`，操作时校验 | `app/ai_service/agent_tools.py` |
| Redis 缓存 | Key 命名空间隔离（`session:{user_id}:*` 等） | `app/db/redis_client.py`、`app/utils/auth_utils.py` |
| 附件/工具文件 | 按 `{user_id}` 目录隔离 + 归属校验（PPT/TTS/聊天附件） | `ppt_router.py`、`tts_router.py`、`chat_attachment_service.py` |

### 1.2 存在的隔离风险 ⚠️

#### 风险 1：全局单例共享 — 影响等级：中

**现状**：`BackgroundInitManager`（[main.py](../main.py)）和 `VectorStoreService`（[app/rag/vector_store.py](../app/rag/vector_store.py)）是进程级全局单例。所有用户的请求共享同一个 `chat_model`、`embed_model`、`rag_service` 实例。

**隐患**：
- Embedding 缓存（`_embedding_cache`）是全局的，A 用户的嵌入结果可能被 B 用户的时间窗口命中（缓存 key 为文本 MD5，内容相同则嵌入相同，但缓存驱逐受全局负载影响）
- 如果未来某个模型实例内部维护了请求级状态（如 conversation context），会导致跨用户数据泄漏

**建议**：
- 当前 LangChain 模型是无状态的，暂时安全。但需在代码规范中明确：**禁止在全局模型实例上存储请求级状态**
- Embedding 缓存可改为 LRU 上限（如 10000 条），防止内存无限增长
- 在 CI 中加入检查：扫描 `BackgroundInitManager` 和 `VectorStoreService` 的修改，确保不会引入有状态字段

---

#### 风险 2：Agent 工具注入的 user_id 依赖闭包 — 影响等级：低

**现状**：`create_agent_tools()`（[app/ai_service/agent_tools.py](../app/ai_service/agent_tools.py)）通过闭包捕获 `user_id`，每次调用创建新的工具实例。

**隐患**：
- 如果未来有人将工具实例缓存复用（如"优化性能"），会导致 A 用户的工具在 B 用户的请求中被调用
- `asyncio.create_task` 启动的后台任务（如 `_sync_to_vector`、`_auto_tag_and_review`）捕获了 `note` 对象，其中包含 `note.user_id`，不会泄漏，但缺乏失败监控（见审查 M9：fire-and-forget 任务无边界）

**建议**：
- 在工具函数内部添加 `assert user_id is not None` 防御性检查
- 后台任务注册到受控的 `asyncio.TaskGroup`（上限 + 失败告警），任务内禁止引用请求级 ORM 对象（改传 ID 重新查询）

---

#### 风险 3：SSE 连接无用户级并发限制 — 影响等级：中（已部分缓解）

**现状**：`/chat/query` 已有进程内并发计数 `_sse_active_counts`（[app/routers/chat.py](../app/routers/chat.py)），单进程内每用户限制 3 个 SSE 连接。

**隐患**：
- 计数为**进程内 dict 无锁**：多 worker / 多实例部署时各进程独立计数，限制形同虚设
- 单进程部署下仍有效，但恶意用户可开满 3 条连接占用 LLM 调用额度

**建议**：
- 计数迁移至 Redis（`INCR` + `EXPIRE`），多进程部署后天然生效（见审查 M11）
- 或由网关层（Nginx limit_conn）限制

---

#### 风险 4：知识库上传无用户配额限制 — 影响等级：低（已解决 ✅）

**现状（已解决）**：
- 单文件大小上限：`MAX_UPLOAD_SIZE_MB=50`，且改为**分块限流读取**（超限立即 413，防内存 DoS，见审查 P0-5）
- 用户级存储配额：`USER_STORAGE_QUOTA_MB=500`（聊天附件按用户统计）
- 上传类型白名单 + magic bytes 双重校验（`app/utils/file_handler.py`）
- 上传接口已挂 Redis 限流（`rate_limit`）

**遗留**：知识库文档列表无分页（文档多时响应体膨胀，见审查 M14），不影响安全。

---

#### 风险 5：全局 Prompt 和配置缓存无用户隔离意识 — 影响等级：低

**现状**：`app/utils/config.py` 的 YAML 配置是进程级全局缓存，`app/utils/prompt_loader.py` 的 prompt 模板也是全局加载。

**隐患**：
- 如果未来支持租户级自定义 prompt，当前架构无法支持
- 当前单租户场景下安全，但需注意日志中不要记录用户敏感信息（已有敏感字段脱敏，见 `logger_handler.SensitiveFilter`）

---

#### 风险 6（新增）：MCP 抓取工具可被用于 SSRF — 影响等级：高（已解决 ✅）

**现状（已解决）**：`fetch` / `tavily_extract` 等 URL 抓取工具已加 **SSRF 地址守卫**（[app/utils/ssrf_guard.py](../app/utils/ssrf_guard.py)，注册时包装所有含 `url` 参数的工具）：拒绝私网/回环/云元数据地址（169.254.0.0/16、10/8、172.16/12、192.168/16、127/8、::1），仅允许公网 http/https，DNS 解析后校验。`fetch` server 补充 `tools_include` 白名单。

**遗留**：DNS rebinding 理论残余风险（解析后域名 IP 变化），彻底防御需在连接层再次校验（见审查 P0-7）。

---

#### 风险 7（新增）：工具产出文件残留 — 影响等级：中（已解决 ✅）

**现状（已解决）**：
- 删除会话时级联清理 PPT/TTS 物理文件（`cleanup_session_tool_files`，2026-08-09 修复）
- TTS 文件新增 TTL（24h）+ 每用户配额（50 个）清理，生成时 + 每日定时任务双保险
- PPT 原有 TTL + 配额机制保持

## 二、回复效率分析与优化方案

### 2.1 当前请求链路 Latency 拆解

一个典型 `/chat/query` 请求的时间消耗：

```
用户发送消息
  │
  ├─ [0-5ms]   JWT 认证 + 会话创建/获取
  ├─ [0-30s]   等待 AI 模型就绪（首次请求，后续 0ms）
  │
  ├─ 并行阶段 (asyncio.gather) ─────────────────────┐
  │  ├─ RAG 检索管线                                  │
  │  │   ├─ route_score (embedding API ~100-300ms)    │
  │  │   ├─ HyDE (LLM ~500-2000ms, 可选)              │
  │  │   ├─ 双源检索 (embedding ~100ms)               │
  │  │   ├─ 重排序 (CrossEncoder ~50-200ms)           │
  │  │   └─ 总结 (LLM ~1000-3000ms, 可选)             │
  │  │                                                │
  │  └─ 记忆压缩                                      │
  │      ├─ DB 查询 (~5-20ms)                         │
  │      ├─ Token 计算 (~1ms)                         │
  │      └─ 滑动窗口构建 (~1ms)                       │
  └──────────────────────────────────────────────────┘
  │
  ├─ [~100-500ms] 查询分类 (L1 规则 <1ms 或 L2 LLM)
  │
  ├─ Agent 执行 (核心耗时)
  │  ├─ ReAct: 1-5 轮 LLM 调用，每轮 ~2-8s
  │  └─ Plan-Execute: 1×Plan + N×Execute + 1×Synthesize (~10-60s)
  │
  └─ 异步后台 (非阻塞)
     ├─ 标题生成 (LLM ~500-2000ms)
     ├─ 消息持久化 (DB ~5-10ms)
     └─ 摘要检查 (条件触发，LLM ~2000-5000ms)
```

### 2.2 已实现的优化 ✅

| 优化项 | 实现方式 |
|--------|----------|
| 启动预热 | 后台异步初始化，不阻塞 HTTP 服务启动 |
| RAG + 记忆压缩并行 | `asyncio.gather` 消除串行等待 |
| 工具按需加载 | 关键词路由匹配，减少 tool definition token 消耗 |
| Embedding 缓存 | 5 分钟 TTL，相同文本免重复调用 API |
| RagService 复用 | 不每次请求重建，避免 ChromaDB 重连 |
| Token 预算管理 | 滑动窗口截断 + 里程碑摘要，控制上下文大小 |
| 异步副作用 | 标题生成、消息保存、摘要生成均非阻塞 |
| 连续工具调用检测 | 6 次上限，防止 Agent 死循环 |
| MySQL 连接池扩容 | `pool_size=20 + max_overflow=30` + `pool_pre_ping` + `pool_recycle`（2026-08 已落地） |
| 流式超时配置 | `LLM_STREAM_TIMEOUT`（默认 120s）经环境变量可调 |

### 2.3 可优化项 🔧

#### 优化 1：添加语义缓存层 — 优先级：高，预计收益 15-30% 延迟降低

**问题**：相同或高度相似的用户查询（如"帮我总结一下笔记"）每次都会走完整管线。

**方案**：
- 对 RAG 检索结果和 Agent 最终回复建立语义缓存
- 使用 `embedding(query)` 的最近邻匹配，阈值 > 0.95 时直接返回缓存
- Redis 存储，TTL 建议 10-30 分钟
- 注意：只缓存"只读"类查询（判断依据：QueryClassifier 分类为 simple 且不含写工具关键词）

**实现要点**：
```
Key: semantic_cache:{query_hash}
Value: {"response": "...", "rag_context": "...", "sources": [...]}
TTL: 600s (10min)
命中条件: cosine_similarity > 0.95
```

---

#### 优化 2：流式响应首 Token 延迟优化 — 优先级：高，预计收益 20-40% 首 Token 加速

**问题**：当前 SSE 流式输出前，需要等待 RAG + 记忆压缩 + 查询分类全部完成，首 Token 延迟 = RAG 耗时 + 分类耗时 + 第一次 LLM 调用延迟。

**方案 A — 提前发送思考事件**（低成本，已部分实现）：
- 当前已在发送 `thinking` 事件，但可以更早发送（如 JWT 验证后立即发送 `connecting` 事件）
- 让前端显示"正在连接 AI..."而不是空白等待

**方案 B — RAG 结果流式注入**（中成本）：
- 不等 RAG 完整完成，分阶段注入：先注入检索结果（不等总结），Agent 可先开始思考
- HyDE 和总结改为可选增强，超时 2s 未完成则跳过

**方案 C — Speculative Decoding**（高成本）：
- 使用小模型（classifier_model / plan_model）先快速生成草稿，大模型校正
- 适合简单问候类查询

---

#### 优化 3：LLM 连接池 & HTTP/2 多路复用 — 优先级：中，预计收益 10-20% 网络延迟降低

**问题**：[app/utils/factory.py](../app/utils/factory.py) 已使用共享 `httpx.AsyncClient`（100 连接池），但以下场景仍有优化空间：
- 标题生成 + 摘要生成 + Agent 执行可能同时使用 LLM，共享连接池需排队
- DashScope API 的 TCP 连接建立耗时约 50-150ms

**方案**：
- 确保 `httpx.AsyncClient` 启用 HTTP/2（`http2=True`），支持多路复用
- 预热连接池：启动时发送一个轻量请求保持连接活跃
- 对 DashScope 配置 `keepalive_expiry` 为 300s（当前默认可能更短）

---

#### 优化 4：MySQL 连接池策略调整 — 已完成 ✅

**状态**：`pool_size=20 + max_overflow=30`（`app/db/database.py`），支撑约 15-20 并发用户（需 MySQL `max_connections >= 200`）。`pool_pre_ping` 自动重连、`pool_recycle=3600` 防 8 小时断连。2026-08 审查确认已达生产级配置，本条关闭。

---

#### 优化 5：ChromaDB 读写分离 — 优先级：中

**问题**：`VectorStoreService` 是单例，所有读写操作共用同一个 ChromaDB PersistentClient。ChromaDB 的 PersistentClient 在写入时会锁定 Collection。

**方案**：
- 写入操作（笔记同步、知识库上传）使用队列异步批量写入，减轻实时写入压力
- 为高频读取（RAG 检索）设置只读副本（ChromaDB 暂不支持，可考虑 Milvus / Qdrant 迁移，但成本高）
- 短期方案：知识库上传的向量化批次从 20 增大到 50，减少写入次数
- ⚠️ 多进程部署前必须解决：ChromaDB PersistentClient 多进程并发写冲突（见审查 M7）

---

#### 优化 6：Plan-Execute Agent 的 Plan 缓存 — 优先级：中

**问题**：Plan-Execute 模式下，相似复杂查询（如"帮我整理 Python 笔记"）每次都会重新生成 Plan（LLM 调用 ~1-3s）。

**方案**：
- 对生成的 Plan 结构做哈希缓存（`plan_cache:{query_embedding_hash}`）
- 相似度 > 0.9 的查询直接复用 Plan 模板，跳过 Phase 1
- TTL 建议 30 分钟

---

#### 优化 7：SSE 连接的心跳与超时优化 — 优先级：中（部分完成）

**现状**：
- 流式超时：`LLM_STREAM_TIMEOUT` 已配置（默认 120s），Plan-Execute 超时为 2×（见 2.2）
- Nginx 反代 `proxy_read_timeout 300s` + `proxy_buffering off` 已配置（`front/nginx.conf`，SSE 必需）

**遗留**：
- 无 SSE 心跳机制，Nginx/负载均衡器可能在 60s 无数据时断开连接

**方案**：
- 每 15 秒发送空注释 SSE 事件（`: heartbeat\n\n`）保持连接活跃
- 根据 QueryClassifier 结果动态调整超时：simple=60s，complex=180s

---

#### 优化 8：Token 预算计算前置 — 优先级：低

**问题**：[app/services/memory_compressor.py](../app/services/memory_compressor.py) 中 Token 计算使用 `TokenCounter`（tiktoken），每次请求都重新计算。虽然单次 < 1ms，但累积有影响。

**方案**：
- 消息保存时将 token 数也存入数据库（`chat_messages` 已有 `token_count` 字段）
- 压缩时直接 SUM 而非逐条计算

## 五、架构演进建议（长期）

1. **LLM 网关层**：在 Agent 和 LLM Provider 之间插入一层网关，统一管理 API Key、限流、fallback、多模型路由
2. **消息队列**：将知识库向量化、摘要生成等重任务从 `asyncio.create_task` 迁移到 Celery / Redis Stream
3. **WebSocket 替代 SSE**：长连接场景下 WebSocket 双向通信更高效
4. **向量库升级**：ChromaDB → Milvus / Qdrant，支持分布式和读写分离
5. **多租户支持**：如果未来需要 SaaS 化，需从当前 `user_id` 隔离升级为 `tenant_id + user_id` 双层隔离

### 1.2 当前调用链路（chat.py 实际流程）

```
POST /api/v1/chat/query
  │
  ├── 1. RAG路由判断: compute_route_score(query) → 距离>0.5则跳过RAG
  ├── 2. RAG检索 + 记忆压缩 (asyncio.gather 并行)
  │
  ├── 3. QueryClassifier.classify()
  │       L1 规则 → simple/complex/uncertain
  │       L2 LLM  → simple/complex
  │
  ├── 4a. [simple] → execute_agent()
  │       resolve_tool_groups() → 按需加载工具组 → ReAct Agent → SSE流式
  │
  └── 4b. [complex] → execute_plan_agent()
         Phase1: 轻量模型生成计划 → plan_start / plan_step 事件
         Phase2: 拓扑排序 + 并行批次 → plan_step_start/end
                每步调用 execute_agent() (⚠️ 双重路由冲突)
         Phase3: 综合结果 → 流式输出 → plan_complete
         Plan失败 → plan_fallback → 回退 ReAct
```

## 三、当前不需要做的事（明确否定的方向）

### 3.1 引擎抽象层（BaseEngine / EngineRegistry / EngineCapability）

**结论：现阶段不需要。**

理由已在 v2 中详细论证，补充两点：

1. **当前 Service 层已经是"专用工具引擎"**：每个 Service 有明确的输入/输出、内部管线、错误处理和降级策略。再包一层 `BaseEngine` 只是增加间接层。

2. **如果未来确实需要**（触发条件：工具数超过 15 个、需要跨 Service 分布式调用、需要热插拔），演进路径是从现有 Service 提取接口而非从头构建。当前 Service 的方法签名已经是天然的引擎契约。

## 四、已知风险清单（代码级）

### 4.1 风险 1（高）：Plan-Execute 与 tool_groups 双重路由冲突

**位置：** [plan_execute_agent.py L196](app/ai_service/plan_execute_agent.py#L196) + [agent_runner.py L98](app/ai_service/agent_runner.py#L98)

**问题：** Plan-Execute 的 `_execute_step()` 调用 `execute_agent()` 时传入：
```python
user_message=f"{user_message}\n\n请重点完成：{step.action}"
```
而 `execute_agent()` 内部调用 `resolve_tool_groups(user_message)` 做关键词匹配。拼接后的文本同时包含原始消息和步骤 action 中的关键词，导致工具路由结果不可预测。

**触发条件示例：**
- 用户："帮我搜索笔记并创建总结" → Plan → step1: "搜索笔记"、step2: "创建总结"
- step2 的 `user_message` 包含原始消息的"搜索"→ `resolve_tool_groups()` 会加载 `note_read` 组，即使 step2 只需要 `note_write`

**建议修复：** 在 `execute_agent()` 中增加 `override_groups` 参数，Plan-Execute 的 `_execute_step()` 根据 `step.tool` 字段直接指定工具组，跳过关键词匹配。预估 ~50 行改动。

### 4.2 ~~风险 2：`create_agent` API 来源不明~~ ✅ 已关闭

**位置：** [agent.py L43](app/ai_service/agent.py#L43)

```python
from langchain.agents import create_agent
```

**验证结果（2026-07-28）：** 已通过 pip 版本确认，`create_agent` 是 langchain 1.3.14 的官方 API：

| 包 | 实际安装版本 |
|---|-------------|
| langchain | **1.3.14** |
| langchain-core | 1.4.9 |
| langgraph | **1.2.9** |

**结论：**
- `create_agent` 位于 `langchain/agents/factory.py`，是 langchain 1.3 新增的**高层封装 API**
- 底层自动调用 LangGraph 的 `create_react_agent`，返回 `CompiledStateGraph`
- 参数 `model`、`tools`、`system_prompt` 与项目代码完全匹配
- 项目对 `astream_events`、`recursion_limit` 等的使用方式均符合规范
- **无需任何修改。**

> **注意：** `requirements.txt` 中写的是 `langchain>=0.3.0`（旧版约束），但实际安装的是 1.3.14。应更新 `requirements.txt` 中的版本约束以反映真实依赖（见风险 3）。

### 4.3 风险 3（中）：`requirements.txt` 版本约束滞后于实际安装版本

**位置：** [requirements.txt](requirements.txt)

**问题：** `requirements.txt` 使用旧版约束：
```
langchain>=0.3.0       # 实际安装 1.3.14
langgraph>=0.3.0       # 实际安装 1.2.9
```

虽然 `>=0.3.0` 在语义上包含了 1.3.14，但任何重新 `pip install` 可能安装到 0.3.x 而非已验证的 1.3.14，导致 `create_agent` 不可用（该 API 是 1.3 新增的）。

**建议：** 更新 `requirements.txt` 为已验证的真实版本：
```
langchain>=1.3.0,<2.0.0
langgraph>=1.2.0,<2.0.0
```
这确保 `create_agent` API 始终可用，同时允许小版本安全更新。

### 4.4 风险 4（中）：Plan 步骤并行写入数据库冲突

**位置：** [plan_execute_agent.py L271-307](app/ai_service/plan_execute_agent.py#L271-L307)

**问题：** 并行模式下多个步骤通过 `asyncio.create_task()` 并发执行。虽然每个工具调用使用独立的 `async with db_session_factory() as db:` 会话，但并行写入仍可能导致：
- MySQL 行锁竞争（如两个步骤同时更新同一用户的不同笔记）
- ChromaDB 写入冲突（底层 SQLite 并发写入能力有限）

**当前缓解：** 每个工具调用使用独立 session，事务边界清晰。

**建议增强：** 在并行批次执行前检查步骤的 `tool` 字段，如果同批次包含多个写工具（`create_note_tool` / `update_note_tool` / `mark_reviewed_tool`），将其降级为顺序执行。预估 ~30 行改动。

### 4.5 风险 5（中）：QueryClassifier 两套关键词列表不一致

**位置：** [query_classifier.py L116](app/ai_service/query_classifier.py#L116) vs [query_classifier.py L144](app/ai_service/query_classifier.py#L144)

**问题：** 同一个方法中定义了两套不同的工具关键词列表，内容不一致：
```python
# L116: 用于"多目标并列"判定
tool_keywords = ["搜索", "搜索笔记", "统计", "回顾", "创建", "更新", "推荐", "标记"]

# L144: 用于"有无工具意图"判定
tool_intentits = ["搜索", "统计", "回顾", "创建", "更新", "推荐", "标记", "时间"]
```

差异：
- L116 有"搜索笔记"，L144 没有（但"搜索"已覆盖）
- L144 有"时间"，L116 没有

**实际影响：** 如果用户消息仅包含关键词"时间"（如"现在几点了"），`matched_tools`=0 但 `has_tool_intent`=True，导致 L153 的"单步工具操作"判定为 False（因为 `matched_tools==0`），消息进入 `uncertain` 而非 `simple`。这会触发不必要的 L2 LLM 分类。

> **注意：** 这不是 NameError（v2 风险分析中已确认 `matched_tools` 是无条件赋值，L153 引用时必然存在）。问题是逻辑层面的：两套列表导致分类行为不一致。

**建议修复：** 统一为一套关键词列表，或从 `agent.yaml` 的 `tool_routing.keyword_rules` 中动态提取。预估 ~15 行改动。

### 4.6 风险 6（中）：Plan 模型 JSON 输出缺少 tool 名称校验

**位置：** [plan_execute_agent.py L91-95](app/ai_service/plan_execute_agent.py#L91-L95)

**问题：** `_generate_plan()` 依赖轻量模型输出严格 JSON。代码已处理 markdown code block 兼容和 JSON 解析异常（降级为 ReAct），但缺少对 `step.tool` 字段的语义校验：
1. 模型可能输出中文工具名（"搜索笔记"）而非代码中的英文名（"search_notes_tool"）
2. 模型可能输出不存在的工具名
3. 模型可能将多个工具写入同一个 `step.tool` 字段

**当前缓解：** try-catch + 降级为 ReAct（降级率过高会丧失 Plan-Execute 的核心价值）。

**建议修复：** 在 `_generate_plan()` 解析 JSON 后增加 `step.tool` 的校验/映射层：
```python
VALID_TOOLS = {"search_notes_tool", "create_note_tool", ...}
TOOL_ALIASES = {"搜索笔记": "search_notes_tool", "创建笔记": "create_note_tool", ...}
```
预估 ~40 行改动。

### 4.7 风险 7（中）：`init_manager` 全局单例的 stage2 超时约束

**位置：** [chat.py L59](app/routers/chat.py#L59) + [main.py L176](app/routers/chat.py#L59) (chat.py 通过 `from main import init_manager`)

**问题：** `init_manager.chat_model` 在 stage1 初始化，`note_service` 在 stage2 初始化。RAG 检索代码有 `await asyncio.wait_for(init_manager.stage2_complete.wait(), timeout=5)` 保护，但 5 秒在重型模型加载场景下可能不够。

**当前状态：** 这是一个已知的运行时约束，不是 bug。但如果 stage2 初始化偶发超过 5 秒，会导致 RAG 检索被跳过。

**建议：** 将 RAG 初始化的超时时间设为可配置（环境变量 `RAG_INIT_TIMEOUT`），默认保持 5 秒。

### 4.8 风险 8（低）：YAML 配置缓存导致修改后需重启

**位置：** [config.py L42-43](app/utils/config.py#L42-L43)

**问题：** `_yaml_cache` 是模块级字典缓存，修改 `agent.yaml` 中的工具路由规则后需要重启服务才能生效。对于工具路由这种可能需要频繁调优的配置，这是一个隐性约束。

**建议：** 文档注明"配置修改需重启服务"。如需热加载，可在 `load_yaml()` 中增加文件 mtime 检查。

---

### 4.9 风险 9（低）：工具路由关键词匹配的扩展性瓶颈

**位置：** [agent.yaml](config/agent.yaml) → `tool_routing.keyword_rules`

**问题：** 工具路由基于硬编码关键词匹配。当工具数量增长时：
- 新工具需要手动添加关键词
- 关键词可能冲突（"记录"可能匹配 write 也可能匹配 read）
- 不支持否定匹配（"不要创建"中的"创建"会误触发 note_write）

**建议：** 中期考虑将关键词匹配升级为轻量意图分类（可复用 `QueryClassifier` 的 LLM 精判能力）。

## 八、总结

### 8.1 核心判断

> **项目已经具备了"强模型大脑 + 专用工具手脚"架构的雏形。** 分类器、Plan-Execute、工具按需加载、循环检测等关键能力已经落地。当前阶段不应引入新的架构概念层（如引擎抽象），而应聚焦于：
>
> 1. **修复已知风险**：`create_agent` 来源验证、版本锁定、双重路由冲突
> 2. **加固现有实现**：tool 名称校验、关键词列表统一、并行写入保护
> 3. **完善用户体验**：前端进度条、性能测试

### 8.2 架构健康度评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 脑-手分离度 | ⭐⭐⭐⭐ | 分类→规划→执行的分层已形成 |
| 依赖兼容性 | ⭐⭐⭐⭐⭐ | langchain 1.3.14 + langgraph 1.2.9，全部兼容 |
| 代码质量 | ⭐⭐⭐ | 有关键词列表不一致、版本约束滞后等问题 |
| 可扩展性 | ⭐⭐⭐⭐ | 工具按需加载为扩展打下基础 |
| 稳定性 | ⭐⭐⭐⭐ | 核心 API 已验证，主要风险在工具路由层面 |
| 前端-后端对齐 | ⭐⭐ | 15 种 SSE 事件前端尚未全部处理 |

### 8.3 最重要的三件事

1. **修复双重路由冲突** — Plan-Execute 的每步应该精确加载工具，而非依赖关键词猜测
2. **更新 requirements.txt 版本约束** — 当前写的是 `>=0.3.0` 但实际依赖 >=1.3.0（`create_agent` 从 1.3 开始存在）
3. **前端 Plan 进度条** — 15 种 SSE 事件中，Plan 相关的 8 种事件前端尚未展示

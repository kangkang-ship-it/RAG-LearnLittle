# RAG Learn Little — 智能笔记助手 · 系统架构设计


> **RAG Learn little** 是一款 AI 驱动的个人知识管理工具，融合笔记管理、RAG 知识库、AI 写作辅助与间隔重复回顾，致力于解决"笔记写了从不回看、知识散落成孤岛"的问题。本文档为该项目的后端设计思路。

---

## 一、项目概述

| 项目 | 说明 |
|------|------| 
| **项目名称** | RAG LearnLittle — 智能笔记助手 |
| **定位** | AI 驱动的个人知识管理工具，融合笔记管理 + RAG 知识库 + AI 写作辅助 + 间隔重复回顾 |
| **核心问题** | 解决"笔记写了从不回看、知识散落成孤岛"的痛点 |
| **架构风格** | 典型的前后端分离架构（SPA + REST API），后端提供 RESTful API 和 SSE 流式接口，前端通过 Axios + 原生 Fetch 消费接口 |
| **性能目标** | 首条消息 TTFB < 3s；语义搜索延迟 < 500ms；知识库文档导入 > 10 页/s |
| **成本目标** | 本地 Ollama 模式下 Chat + Embedding API 费用为零；云端 Fallback 仅作容灾备选 |

### 2.2 应用入口与生命周期

`main.py` 中定义了完整的应用生命周期：

#### 1. 启动阶段（`startup_event`）

- 加载 `.env` 环境变量
- 初始化数据库表结构（`init_db` — `create_all` + 自动补列迁移）
- 创建测试用户 `admin / admin1234`  # 本地部署先暂时使用这个用户，在向数据中添加数据的时候写成一个单测；项目启动的时候不需要再次添加，main函数拉起整个项目
- 初始化数据库会话管理器
- 连接 Redis
- 后台异步启动重型资源初始化（模型加载、ChromaDB、重排序模型）

#### 2. 中间件

- CORS 中间件（本地开发允许所有源，生产环境通过 `CORS_ORIGINS` 环境变量白名单控制）
- 请求处理时间中间件（`X-Process-Time` 响应头）
- 全局异常处理器（`register_exception_handlers`）

#### 3. 关闭阶段（`shutdown_event`）

- 关闭 Redis 连接池
- 释放 SQLAlchemy 异步引擎连接池

### 2.3 后台初始化管理器

`_BackgroundInitManager` 是一个核心设计，解决了重型资源阻塞启动的问题：

- 在 FastAPI 启动后通过 `asyncio.create_task` 在后台异步初始化
- 分三个阶段顺序执行：**(1)** AI 模型 → **(2)** NoteService / ChromaDB → **(3)** 重排序模型
- 每个阶段完成后设置 `asyncio.Event`，路由层通过 `await event.wait()` 阻塞等待
- 管理的实例：`chat_model`, `embed_model`, `vision_model`, `note_service`, `reorder_service`
- **Ollama 模型就绪检查：** 初始化时检查 Chat 和 Embedding 模型是否存在（`ollama list`），不存在则自动 `ollama pull` 下载，下载进度通过日志输出
- **Embedding 一致性校验：** 若 ChromaDB 已有向量数据，校验当前 `EMBED_PROVIDER` + `OLLAMA_EMBED_MODEL` 与向量库记录的来源是否一致；不一致则**拒绝启动**并提示"请删除 `data/chroma/` 后重新导入知识库"，防止语义搜索静默失效

## 三、认证与 API 规范

### 3.1 JWT 认证流程

```
用户登录 POST /auth/login
  │
  ▼
┌─────────────────────────────────┐
│  校验 username + password        │
│  └─ 失败 → 401 + 错误计数 +1     │
│  └─ 成功 → 生成令牌对             │
└─────────────┬───────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│  Access Token  (TTL 30 分钟)     │  ← 短生命周期，降低泄露风险
│  Refresh Token (TTL 7 天)        │  ← 长生命周期，存 Redis 白名单
│  均以 JWT 形式返回               │
└─────────────┬───────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│  前端存储策略                     │
│  Access Token  → 内存变量        │  ← 避免 XSS
│  Refresh Token → httpOnly Cookie │  ← 避免 JS 读取
└─────────────────────────────────┘
```

| 维度 | 策略 |
|------|------|
| **Access Token** | JWT，TTL 30 分钟，payload 含 `user_id` + `exp`，每次请求通过 `Authorization: Bearer <token>` 携带 |
| **Refresh Token** | JWT，TTL 7 天，服务端存 Redis 白名单（`refresh_token:{user_id}:{jti}`），续期时校验是否在白名单内 |
| **刷新接口** | `POST /auth/refresh` — 校验 Refresh Token → 签发新 Access Token + 新 Refresh Token（旧 Refresh Token 立即失效，Rotation 防重放） |
| **登出接口** | `POST /auth/logout` — 从 Redis 删除 Refresh Token 白名单记录，Access Token 加入黑名单（TTL = 剩余有效期） |

### 3.2 密码安全策略

| 维度 | 策略 |
|------|------|
| **哈希算法** | bcrypt（cost factor = 12） |
| **最小长度** | 8 位 |
| **复杂度要求** | 至少包含字母 + 数字 |
| **登录锁定** | 连续 5 次失败 → 锁定 15 分钟（Redis 计数 `login_attempts:{username}`，TTL 900s） |
| **密码修改** | 需提供旧密码验证；修改后所有 Refresh Token 立即失效 |

### 3.3 API 响应规范

#### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... },
  "request_id": "uuid"
}
```

#### 失败响应

```json
{
  "code": 40101,
  "message": "Access Token 已过期",
  "detail": "Token expired at 2026-07-19T10:30:00Z",
  "request_id": "uuid"
}
```

#### 错误码体系

| 码段 | 含义 | 示例 |
|------|------|------|
| `0` | 成功 | — |
| `400xx` | 请求参数错误 | 40001 缺少必填字段、40002 格式校验失败 |
| `401xx` | 认证失败 | 40101 Token 过期、40102 Token 无效、40103 密码错误 |
| `403xx` | 权限不足 | 40301 无权访问该笔记、40302 上传配额已满 |
| `404xx` | 资源不存在 | 40401 笔记不存在、40402 会话不存在 |
| `409xx` | 冲突 | 40901 用户名已存在、40902 幂等键重复 |
| `429xx` | 限流 | 42901 全局频率限制、42902 单接口频率限制 |
| `500xx` | 服务端错误 | 50001 内部错误、50002 LLM 调用失败 |

### 3.4 限流策略

基于令牌桶算法，分两个层级：

| 层级 | 默认限制 | Redis Key | 用途 |
|------|----------|-----------|------|
| **全局** | 100 次 / 分钟 / 用户 | `rate_limit:{user_id}:global` | 防止单用户打爆服务 |
| **接口级** | 按端点差异化配置 | `rate_limit:{user_id}:{endpoint}` | 保护高成本接口 |

| 端点 | 限制 | 原因 |
|------|------|------|
| `/chat`（Agent 对话，Ollama 正常） | 10 次 / 分钟 | LLM 调用成本适中 |
| `/chat`（Agent 对话，Fallback 到 DashScope） | `DASHSCOPE_FALLBACK_RATE_LIMIT`（默认 5 次 / 分钟） | Ollama 不可用时自动收紧，防账单失控 |
| `/knowledge/upload` | 20 次 / 分钟 | 文件处理消耗大 |
| `/note`（CRUD） | 60 次 / 分钟 | 常规操作放宽 |
| `/auth/*`（登录/注册） | 5 次 / 分钟 | 防暴力破解 |
| 其他 | 30 次 / 分钟 | 默认 |

## 四、后端各模块职责详解

### 4.1 Router 层（路由 / API 层）

路由层负责 HTTP 请求接收、参数校验、权限认证、限流、调用 Service 层、封装响应。

**API 版本管理：** 所有路由统一使用 `/api/v1` 前缀（如 `/api/v1/chat`），后续 breaking change 通过 `/api/v2` 平滑迁移，旧版本保留 6 个月过渡期。

| 路由文件 | 前缀 | 核心端点 |
|----------|------|----------|
| `chat.py` | `/chat` | Agent 流式对话、RAG 查询、会话管理、文档重排序 |
| `note_router.py` | `/note` | 笔记 CRUD、语义搜索、自动标签、内联补全、AI 写作辅助、批量操作、关联推荐、Markdown 导出 |
| `knowledge_router.py` | `/knowledge` | 知识库文档上传（单 / 多文件）、文档列表 / 详情 / 切片、MD5 管理、图片服务 |
| `review_router.py` | `/review` | 间隔重复回顾：今日待回顾、标记完成、生成回顾问题 |
| `user.py` | `/user`, `/auth`, `/file` | 用户注册 / 登录 / 登出 / Token 刷新 / 详情 / 更新、文件上传 |
| `note_template_router.py` | `/note-template` | 笔记模板 CRUD、排序 |
| `health.py` | `/health`（liveness）、`/ready`（readiness） | `/health` 始终 200 确认进程存活；`/ready` 在后台初始化全部完成后才返回 200，供负载均衡器 / 容器编排就绪探测 |

**设计特点：**

- 统一使用 `Depends(get_current_user_id)` 进行 JWT 身份认证
- 统一使用 `Depends(rate_limit(...))` 进行接口限流（令牌桶算法）
- 统一使用 `success_response()` 封装响应格式
- 流式接口返回 `StreamingResponse`（SSE 格式 `text/event-stream`）

### 4.2 Services 层（业务逻辑层）

| 服务文件 | 职责 |
|----------|------|
| `note_service.py` | 笔记核心业务：CRUD + ChromaDB 向量双写 + 异步自动标签生成（LLM）+ 语义搜索 + 关联推荐 + AI 内联补全 + AI 写作辅助（SSE）+ 批量操作 + Markdown 导出 |
| `review_service.py` | 间隔重复回顾：艾宾浩斯遗忘曲线算法（1 / 2 / 4 / 7 / 15 / 30 天） |
| `database_session_manager.py` | 聊天会话持久化：会话创建 / 消息存储 / 历史查询 / 会话删除，基于 MySQL |
| `chat_service.py` | 聊天路由的业务代理层，封装 RAG 查询和会话管理逻辑 |
| `note_template_service.py` | 笔记模板业务逻辑 |

#### NoteService 核心设计

- **向量双写：** 笔记创建 / 更新时 先写MySQL → 异步写入ChromeDB → 失败时标记待修复 `notes_collection`
- **异步自动标签：** 保存笔记后立即返回，通过 `asyncio.create_task` 在后台调用 LLM 生成标签和分类，同时创建回顾记录，如果有异常就捕获异常并记录日志、考虑用任务队列（ARQ/Celery）保证重试。
- **语义搜索：** ChromaDB 向量检索 → 提取 `note_id` → MySQL 回填完整数据
- **关联推荐：** 同时在 `notes_collection` 和 `rag_collection` 检索，合并后按相似度排序
- **数据导出：** 支持按分类 / 全部导出笔记为 Markdown 或 JSON，打包为 ZIP 下载（异步任务，生成完成后通知用户）

#### 会话与消息管理设计

##### 1. 消息写入路径（MySQL 优先）

```
用户发送消息
  │
  ▼
┌─────────────────────────────┐
│  1. 同步写入 MySQL            │  ← 保证数据不丢
│     INSERT INTO chat_messages │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  2. 同步 / 异步更新 Redis     │  ← 失败不影响数据完整性
│     LPUSH + LTRIM 保持 10 条  │     下次读取时从 MySQL 回填
└─────────────────────────────┘
```

- **写路径：** 先同步写 MySQL → 再更新 Redis 热缓存（Redis 更新失败仅记录日志，不重试，下次读请求触发回填即可）
- **幂等性：** `chat_messages` 表增加 `idempotency_key`（客户端生成 UUID），写入前先检查是否已存在，防止网络重试导致重复消息

##### 2. 消息读取路径（Redis 热缓存 + MySQL 回源）

```
key:  chat:msgs:{session_id}
类型: Redis List
内容: [msg_10_json, msg_9_json, ..., msg_1_json]  （最新在左）
策略: 每次 LPUSH 后执行 LTRIM 保持 10 条上限
可配置: REDIS_CHAT_BUFFER_SIZE = 10
```

| 读取场景 | 流程 |
|----------|------|
| **最近消息（大概率）** | 读 Redis List → 命中则直接返回 |
| **缓存 miss** | Redis 为空 → 查 MySQL `SELECT ... ORDER BY created_at DESC LIMIT 10` → 写回 Redis → 返回 |
| **翻历史记录** | 跳过 Redis，直接走 MySQL 游标分页 |

##### 3. 游标分页（翻历史消息）

不使用 `LIMIT/OFFSET`（翻页时新消息插入会导致重复或遗漏），改用游标分页：

```
GET /chat/{session_id}/messages?cursor={created_at}&limit=20

MySQL 查询：
SELECT * FROM chat_messages
WHERE session_id = ? AND created_at < ?
ORDER BY created_at DESC
LIMIT 20
```

前端传递上一页最早一条消息的 `created_at` 作为游标，保证翻页一致性。

##### 4. 会话标题自动生成

| 维度 | 策略 |
|------|------|
| **触发时机** | 会话首条用户消息发送后，异步调用 LLM 生成标题（仅此一次） |
| **冻结机制** | 生成后在 `chat_sessions.metadata` 中记录 `title_generated_at`，标题不再自动更新（用户可手动修改） |
| **失败兜底** | LLM 超时或返回空 → 截取首条用户消息前 30 字符作为降级标题 |
| **Prompt** | 见 4.11 节 `session_title_prompt.txt`：不超过 20 字概括主题，用用户语言，不加引号 |

##### 5. ChatSession.metadata 字段定义

```json
{
  "title_generated_at": "2026-07-19T10:30:00Z",
  "title_frozen": true,
  "model_name": "qwen3-max",
  "total_tokens": 15230,
  "message_count": 42
}
```

##### 6. 会话列表缓存

用户打开侧边栏时加载会话列表（`ORDER BY updated_at DESC`）——高频查询，加 Redis 缓存：

```
key:       chat:sessions:{user_id}
类型:      Redis String (JSON Array)
内容:      [{id, title, updated_at, message_count, metadata}, ...]
TTL:       300s（5 分钟）
失效策略:  新消息写入或标题变更时主动删除该缓存（delete_pattern "chat:sessions:{user_id}*"）
```

##### 7. 相对时间展示

后端只提供精确的 `updated_at`（UTC），前端计算相对时间标签：

```
diff = now() - updated_at
< 1 天   → "X 小时前"
< 1 周   → "X 天前"
< 1 月   → "X 周前"
< 1 年   → "X 个月前"
≥ 1 年   → "X 年前"
```

不在后端计算是为保持 API 纯数据职责，避免国际化耦合。

### 4.3 Models 层（数据模型层）

基于 SQLAlchemy 2.0 声明式 ORM，所有模型共享同一个 `Base`。

| 模型 | 表名 | 核心字段 | 外键（ON DELETE） | 备注 |
|------|------|----------|-------------------|------|
| User | `users` | uuid(PK), username, email, password(bcrypt), avatar, bio, status, created_at, updated_at | — | — |
| Note | `notes` | id(UUID PK), title, content(Text), tags(JSON), category, is_pinned, deleted_at, created_at, updated_at | `user_id` → users.uuid (CASCADE) | `deleted_at` 非 NULL 视为软删除 |
| ChatSession | `chat_sessions` | id(UUID PK), title, metadata(JSON), created_at, updated_at | `user_id` → users.uuid (CASCADE) | `messages` 由 ORM relationship 关联 |
| ChatMessage | `chat_messages` | id(自增 PK), role, content(Text), token_count, idempotency_key, created_at | `session_id` → chat_sessions.id (CASCADE) | `created_at` 作为消息排序依据；`idempotency_key` 有 UNIQUE 约束防重复写入 |
| ReviewRecord | `review_records` | id(自增 PK), review_count, interval_days, quality(0–5), next_review_at, reviewed_at, created_at, updated_at | `note_id` → notes.id (CASCADE), `user_id` → users.uuid (CASCADE) | `quality` 为 SM-2 算法升级预留；`reviewed_at` 记录实际完成时间 |
| NoteTemplate | `note_templates` | id(自增 PK), name, content_structure(JSON), category, sort_order, created_at, updated_at | `user_id` → users.uuid (CASCADE) | `content_structure` 存储模板骨架（Markdown / JSON Schema） |
| KnowledgeDocument | `knowledge_documents` | id(自增 PK), filename, file_path, file_size, file_type, md5_hash, chunk_count, created_at, updated_at | `user_id` → users.uuid (CASCADE) | 知识库文档元数据，向量存在 ChromaDB `rag_collection` 中 |

> **数据库迁移策略：** 非 Alembic，而是自建的轻量级方案 — `create_all` 建表 + `_migrate_columns` 自动补列（`ALTER TABLE ADD COLUMN`），注意问题：迁移版本记录，回滚能力、非空列需要默认值，自动补列可能给null，导致现有查询崩溃。

### 4.4 RAG 层（RAG 核心功能）

这是整个系统**最核心**的模块，实现了完整的 RAG 管线。

#### RagService（`rag_service.py`）

- **HyDE 技术：** 先让 LLM 生成假设性回答，再用假设性回答去向量库检索，提升检索准确率
- **双源检索：** 同时从知识库（`rag_collection`）和笔记库（`notes_collection`）检索，合并结果并标记来源
- **重排序：** 使用 CrossEncoder（`BAAI/bge-reranker-v2-m3`）对检索结果重排序
- **分批总结：** 对 Top 3 文档并发总结，再合并生成最终回答
- **思考过程推送：** 通过 `thinking_callback` 实时向前端推送思考阶段事件

#### VectorStoreService（`vector_store.py`）

- **线程安全单例：** 双重检查锁定模式，避免 ChromaDB 多实例冲突
- **自我修复：** 初始化失败时自动删除并重建 ChromaDB（⚠️ 仅限确认数据损坏时触发；磁盘满 / 权限错误等环境问题跳过此逻辑，保留数据并报错）
- **延迟嵌入：** `_LazyEmbedding` 包装器将嵌入模型解析推迟到首次调用
- **混合检索：** `HybridRetriever` 实现 BM25 + 向量的 `EnsembleRetriever`
- **动态权重：** 根据查询长度和词密度动态调整向量 / BM25 权重（长查询偏向向量，短查询偏向 BM25）
- **路由决策：** `compute_route_score` 通过 Top-1 L2 距离判断是否需要 RAG 管线（阈值 `RAG_ROUTE_THRESHOLD` 在 `.env` 可配置，默认 0.5；更换 Embedding 模型后必须重新校准）
- **MD5 去重：** 通过 `MD5Store` 实现文档去重上传
- **用户隔离：** 所有检索和操作都通过 `user_id` metadata 过滤

#### TextSplitter（`text_spliter.py`）

- 基于 LangChain `RecursiveCharacterTextSplitter`
- 支持语义优化：相邻片段余弦相似度 > 0.7 时自动合并
- 支持异步和同步两种分割模式

#### TaskQueue（`task_queue.py`）

- 线程安全的任务队列，协调多线程切片和单线程写入之间的数据传递

#### 知识库文档处理管线

#### SSE 认证方式

`EventSource` API 不支持自定义 HTTP Header，JWT 不能通过 `Authorization` header 传递。采用短期 Query Token 方案：

```
GET /api/v1/chat/stream?token={short_lived_token}
```

| 维度 | 策略 |
|------|------|
| **Token 签发** | `POST /auth/sse-token` — 用有效 Access Token 换取短期 SSE Token |
| **TTL** | 60 秒，仅用于建立连接 |
| **一次性** | 连接建立后 Token 立即失效（Redis `sse_token:{jti}` 写入后删除） |

#### SSE 断线重连

| 维度 | 策略 |
|------|------|
| **重连机制** | SSE 连接断开后，前端指数退避重连（1s → 2s → 4s → 8s，上限 30s）；重连前重新获取 SSE Token |
| **消息续传** | 重连时前端携带 `Last-Event-ID` header，后端从该 event_id 之后恢复推送（需在消息表中记录 `event_id`） |
| **兜底** | 若后端无法定位断点（event_id 已过期或不存在），则返回已完成的消息列表（非流式），前端直接渲染最终结果 |

#### LLM 主备切换与熔断降级

`factory.py` 内置 Circuit Breaker 状态机，实现 Chat 模型优先本地 Ollama、不可用时自动降级 DashScope。

##### 核心原则

| 原则 | 说明 |
|------|------|
| **Embedding 不参与切换** | `EMBED_PROVIDER=OLLAMA` 固定使用本地 `nomic-embed-text`，数据不出本机；更改此配置需重建 ChromaDB 全部向量 |
| **Chat 优先本地** | `LLM_STRATEGY=OLLAMA_FIRST`：正常状态使用本地 Ollama，零 API 费用 |
| **Chat 自动降级** | Ollama 不可用时自动切 DashScope，恢复后自动回切 |

##### Circuit Breaker 三态状态机

```
                 连续失败 ≥ THRESHOLD(3次)
     ┌───────────────────────────────────┐
     │                                   │
     ▼                                   │
┌─────────┐                         ┌─────────┐
│ CLOSED  │  正常使用 Ollama          │  OPEN   │  跳过 Ollama
│         │                         │         │  直接用 DashScope
└────┬────┘                         └────┬────┘
     │                                   │
     │                     COOLDOWN(60s) 到期
     │                                   │
     │              ┌─────────┐          │
     │              │HALF_OPEN│  ◄───────┘
     │              │试探 1 次  │
     │              └────┬────┘
     │          成功 /    \ 失败
     │          /          \
     └────────◄            └─────────► 回到 OPEN，重置冷却
   回到 CLOSED
```

| 状态 | 行为 | 状态存储 |
|------|------|----------|
| **CLOSED** | 所有 Chat 请求走 Ollama；失败计数器在 Redis（Key: `cb:chat:{user_id}:failures`，TTL 与窗口绑定） | Redis |
| **OPEN** | 跳过 Ollama，直接走 DashScope；前端收到 `{"event": "fallback", "provider": "aliyun"}` 提示条 | Redis |
| **HALF_OPEN** | 冷却到期后，放行 1 个试探请求到 Ollama → 成功回 CLOSED / 失败回 OPEN | Redis |

##### 触发切换的失败类型

| 失败类型 | 是否计数 | 原因 |
|----------|----------|------|
| Connection Refused / Timeout | ✅ 计数 | Ollama 未启动或卡住 |
| HTTP 5xx | ✅ 计数 | Ollama 内部错误 |
| HTTP 404（模型未找到） | ❌ 不计数，直接报错 | 配置问题，切换没用 |
| 首次请求慢（> 30s 但 < 60s） | ❌ 不计数，延长等待 | 模型冷加载到 GPU |

> **模型未找到的兜底：** 启动阶段已在 2.3 节自动 `ollama pull`，运行时基本不会遇到。

##### Fallback 期间的特殊处理

| 措施 | 说明 |
|------|------|
| **限流收紧** | Fallback 时 Chat 限流从 10 次/分钟 自动收紧为 `DASHSCOPE_FALLBACK_RATE_LIMIT`（默认 5 次/分钟），防止 Ollama 长时间挂掉导致 API 账单失控 |
| **前端通知** | SSE 流中推送 fallback 事件，前端展示"本地模型暂时不可用，已切换至云端"提示，用户有权知道产生了 API 费用 |
| **渐进回切** | HALF_OPEN 试探成功后不立即全量切回 → 先放 20% 流量回 Ollama → 观察 3 分钟无异常 → 全量切回 CLOSED |

##### Embedding 切换安全锁

启动阶段（2.3 节）增加校验：

```
如果 EMBED_PROVIDER 与 ChromaDB 已有向量来源不一致：
  → 拒绝启动
  → 日志输出：EMBED_PROVIDER 已变更，请删除 data/chroma/ 后重新导入知识库
```

防止用户无意中改了 `EMBED_PROVIDER` 导致所有语义搜索静默失效。

## 六、RAG 流程详解

完整的 RAG 查询流程如下：

```
用户提问
  │
  ▼
┌─────────────────────────────────────────────┐
│  路由决策  compute_route_score               │
│  (Top-1 L2 距离 → 相似度分数)                │
└─────────────────┬───────────────────────────┘
                  │
      ┌───────────┴───────────┐
      │                       │
  score ≤ 0.5             score > 0.5
  跳过 RAG                进入 RAG 前置管线
  直接走 Agent                │
      │                       ▼
      │            ┌─────────────────────┐
      │            │  HyDE               │
      │            │  LLM 生成假设性回答   │
      │            └─────────┬───────────┘
      │                      │
      │                      ▼
      │            ┌─────────────────────────────┐
      │            │  双源检索                     │
      │            │  rag_collection              │
      │            │  + notes_collection           │
      │            │  (按 user_id 过滤，用户隔离)   │
      │            └─────────┬───────────────────┘
      │                      │
      │                      ▼
      │            ┌─────────────────────────────┐
      │            │  混合检索器                   │
      │            │  EnsembleRetriever            │
      │            │  (BM25 + 向量)               │
      │            │  动态权重：长查询→向量(0.7)    │
      │            │  短查询→BM25(0.7)            │
      │            └─────────┬───────────────────┘
      │                      │
      │                      ▼
      │            ┌─────────────────────────────┐
      │            │  重排序                       │
      │            │  CrossEncoder                 │
      │            │  (bge-reranker-v2-m3)         │
      │            └─────────┬───────────────────┘
      │                      │
      │                      ▼
      │            ┌─────────────────────────────┐
      │            │  分批总结                     │
      │            │  Top 3 文档并发总结 → 合并     │
      │            └─────────┬───────────────────┘
      │                      │
      ▼                      ▼
      │            ┌─────────────────────────────┐
      │            │  注入 Agent                   │
      │            │  RAG 上下文作为 system_prompt  │
      │            └─────────┬───────────────────┘
      │                      │
      ▼                      ▼
      │            ┌─────────────────────────────┐
      │            │  Agent 执行                   │
      │            │  可调用 8 种工具，流式输出回答   │
      │            └─────────┬───────────────────┘
      │                      │
      ▼                      ▼
┌─────────────────────────────────────────────┐
│  SSE 推送                                     │
│  thinking 事件 + response chunk → 前端        │
└─────────────────────────────────────────────┘
```

> **思考过程实时推送：** RAG 管线在后台执行时，通过 `asyncio.Queue` + `thinking_callback` 将每个阶段（`retrieval` / `hyde` / `reorder` / `summarize`）的进展实时推送给前端。

## 七、AI Agent 实现方式

| 维度 | 实现 |
|------|------|
| **框架** | LangChain `AgentExecutor` + `create_tool_calling_agent` |
| **模型** | Chat 优先本地 Ollama（`qwen3:latest`），不可用时 Circuit Breaker 自动降级 DashScope（`qwen3-max`），通过 `LLM_STRATEGY` 控制；Embedding 固定本地 Ollama（`nomic-embed-text`） |
| **工具** | 8 个自定义 Tool，覆盖笔记搜索 / 创建 / 统计、回顾管理、关联推荐、用户信息、时间查询 |
| **会话历史** | MySQL 持久化，每次请求从数据库加载历史消息构建 `chat_history` |
| **上下文窗口管理** | 滑动窗口取最近 20 轮对话；超过 20 轮时对早期消息做 LLM 摘要压缩，摘要替换原始消息注入 prompt，原始消息仍保留在 MySQL 供翻历史查看 |
| **流式输出** | `asyncio.Queue` 实现思考过程实时推送 + 回答内容按 15 字符 chunk 模拟流式 |
| **中间件** | LangGraph 生命周期钩子用于日志记录 |
| **RAG 集成** | 路由层先执行 RAG 管线获取上下文，注入 Agent 的 `system_prompt` |

| 维度 | 选型 |

### 8.2 测试分层

| 层级 | 范围 | 策略 |
|------|------|------|
| **单元测试** | Services / Utils / Models | mock 所有外部依赖（DB、Redis、LLM），验证纯业务逻辑 |
| **集成测试** | Router → Service → DB/Redis | 使用真实测试数据库和 Redis，验证端到端数据流 |
| **契约测试** | API 响应格式 | 校验响应 JSON 结构与 Schemas 定义一致（`code`/`message`/`data`/`request_id`） |

### 8.3 测试数据管理

| 维度 | 策略 |
|------|------|
| **Fixtures** | `conftest.py` 提供 `async_client`、`test_db_session`、`test_redis`、`auth_headers` 等共享 fixture |
| **测试用户** | 通过 fixture 动态创建，不依赖启动时的 `admin/admin1234` |
| **数据隔离** | 每个测试模块 `setup` 建表 / `teardown` 清空数据（`TRUNCATE` + ChromaDB `delete_collection`） |
| **LLM Mock** | 预置固定回复（如 `"mock_response": "这是一条模拟的 AI 回答"`），验证工具调用和 prompt 组装正确性 |

### 8.4 关键测试场景

| 场景 | 验证点 |
|------|--------|
| 用户注册 → 登录 → 获取 Token → 访问受保护接口 | 完整认证链路 |

| 间隔重复：生成回顾记录 → 标记完成 → `next_review_at` 更新 | 艾宾浩斯算法正确性 |
| Ollama 超时 → Circuit Breaker OPEN → Fallback DashScope | 主备切换状态机 |
| 超过限流阈值 → 429 响应 | 令牌桶限流 |

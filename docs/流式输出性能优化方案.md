# 流式输出性能优化方案

> 目标：优化首 token 延迟 + LLM API 连接复用，提升对话响应速度  
> 状态：方案阶段（未实施）  
> 日期：2026-07-22

---

## 一、当前请求链路分析

用户发送消息到第一个 token 返回的完整路径：

```
POST /chat/query
  │
  ├─ 1. 会话管理（DB 查询/创建 session）           ~10-30ms
  ├─ 2. 保存用户消息（DB INSERT + Redis LPUSH）     ~10-20ms
  ├─ 3. 等待 AI 模型就绪（stage1_complete event）   已就绪时 ~0ms
  │
  ├─ 4. RAG 检索管线 ───────────────────────────── ~500-3000ms ★ 核心瓶颈
  │   ├─ 4a. 等待 VectorStore 就绪（stage2_complete）
  │   ├─ 4b. 创建 VectorStoreService + RagService 实例
  │   ├─ 4c. 生成查询 Embedding（远程 API 调用）       ~100-300ms
  │   ├─ 4d. ChromaDB 双源检索（knowledge + notes）   ~10-50ms
  │   ├─ 4e. 重排序（CrossEncoder，如有）              ~50-200ms
  │   └─ 4f. 文档并发总结（Top-K 篇 × LLM 调用）     ~500-2000ms ★ 最大瓶颈
  │
  ├─ 5. System Prompt 构造（注入 RAG 上下文）        ~1ms
  │
  ├─ 6. 记忆压缩管线 ───────────────────────────── ~50-200ms
  │   ├─ 6a. Token 预算计算
  │   ├─ 6b. 加载全量消息历史（DB 查询）
  │   ├─ 6c. 加载已有摘要（DB 查询）
  │   └─ 6d. 滑动窗口压缩
  │
  ├─ 7. Agent 创建（create_agent + 工具集绑定）      ~10-50ms
  │
  └─ 8. 流式输出（astream_events）                  ─→ 首 token 到达
```

**关键发现**：步骤 4（RAG）和步骤 6（记忆压缩）**无数据依赖关系**，当前串行执行浪费了 200-500ms。

## 二、瓶颈 1：RAG 检索耗时优化（首 token 延迟）

### 2.1 文档总结阶段延迟最高（预估节省 500-2000ms）

**现状**：[`app/rag/rag_service.py:203-235`](../app/rag/rag_service.py#L203-L235)

检索完成后，`_summarize_documents()` 对 Top-K 篇文档**并发调用 LLM 逐篇总结**，然后合并为最终上下文。虽然 N 篇并发执行，但每篇 LLM 调用都是一次完整的非流式请求-响应，直接阻塞了后续的 Agent 生成。

**问题**：
- 每篇文档总结调用 `chat_model.invoke()`（同步阻塞），底层走 HTTP 请求到远程 API，单次耗时 300-1000ms
- 3 篇文档并发总结，总耗时取决于最慢的那篇（木桶效应）
- 总结阶段完全阻塞首 token 输出

#### 方案 A：轻量级截断替代 LLM 总结（推荐）

将 `_summarize_documents()` 改为**纯文本截断**，不做 LLM 总结。原始文档内容直接注入 system_prompt 的 `<reference>` 块，让 Agent 在生成回答时自行理解和引用。

```python
# 改造思路（不修改代码，仅示意）
async def _summarize_documents(self, query: str, documents: List[dict]) -> str:
    """轻量级：直接截断拼接，不做 LLM 总结"""
    parts = []
    for doc in documents:
        # 每篇文档截断到 500-800 字，保留最相关的内容
        parts.append(doc["content"][:800])
    return "\n\n---\n\n".join(parts)
```

**收益**：首 token 延迟减少 500-2000ms  
**风险**：context 可能变长，token 消耗增加。需配合 Token 预算管理器限制 RAG 上下文长度（当前已有 `rag_context_max=2000` 配置）  
**建议**：添加 `RAG_ENABLE_SUMMARIZE` 环境变量开关，方便 A/B 对比

#### 方案 B：延迟总结（总结与生成并行）

不等待文档总结完成，先将原始截断内容注入 context 开始生成，后台异步完成总结后通过后续消息注入。

**收益**：首 token 延迟减少 500-2000ms，总结结果仍可被后续使用  
**风险**：实现复杂度较高，需要消息级别的上下文更新机制  
**建议**：优先实施方案 A，若上下文质量下降明显再考虑方案 B

### 2.2 Embedding API 调用没有连接复用（预估节省 50-150ms）

**现状**：[`app/rag/vector_store.py:287-307`](../app/rag/vector_store.py#L287-L307)

每次 RAG 查询调用 `_generate_embeddings()`，内部用 `loop.run_in_executor()` 执行同步的 `embed_model.embed_documents()`。底层每次都是独立的 HTTP 请求，无连接池复用，TCP/TLS 握手开销重复发生。

**现状**：[`app/utils/factory.py:129-154`](../app/utils/factory.py#L129-L154)

`DashScopeEmbeddings` 创建时没有传入自定义 `http_client`，使用默认 HTTP 客户端。

#### 方案：配置 Embedding 模型使用共享 httpx 连接池

```python
# 改造思路（不修改代码，仅示意）
import httpx

# 模块级共享 HTTP 客户端
_shared_http_client = httpx.Client(
    timeout=httpx.Timeout(30.0, connect=5.0),
    limits=httpx.Limits(
        max_keepalive_connections=10,
        max_connections=50,
        keepalive_expiry=30,
    ),
)

# 创建 Embedding 模型时传入
DashScopeEmbeddings(
    model=model_name,
    dashscope_api_key=api_key,
    http_client=_shared_http_client,  # 复用连接
)
```

**收益**：首次调用后的后续请求省去 TCP/TLS 握手（约 50-150ms）  
**风险**：极低。需确认 `DashScopeEmbeddings` 支持 `http_client` 参数（底层基于 OpenAI SDK，大概率支持 `http_client` 或 `client` 参数）

#### 补充：Embedding 调用改为原生异步

当前使用 `run_in_executor` 将同步调用扔到线程池，占用线程资源。如果 Embedding 模型底层支持异步（如 `aembed_documents()`），应直接使用异步调用：

```python
# 改造思路
async def _generate_embeddings(self, texts: List[str]) -> List[List[float]]:
    # 直接异步调用，避免线程切换
    return await self.embed_model.aembed_documents(texts)
```

**收益**：减少线程池占用 + 线程切换开销（约 5-20ms）

### 2.3 缺少查询 Embedding 缓存（重复查询场景）

**现状**：每次查询都重新生成 Embedding，即使相同/相似的查询反复出现。

#### 方案：添加内存 LRU 缓存 + TTL

```python
# 改造思路（不修改代码，仅示意）
from functools import lru_cache
import hashlib

# 在 VectorStoreService 中添加
_embedding_cache: Dict[str, tuple] = {}  # key -> (embedding, timestamp)

async def _generate_embeddings_cached(self, texts: List[str]) -> List[List[float]]:
    results = []
    for text in texts:
        cache_key = hashlib.md5(text.encode()).hexdigest()
        cached = self._embedding_cache.get(cache_key)
        if cached and (time.time() - cached[1]) < 300:  # 5 分钟 TTL
            results.append(cached[0])
        else:
            embedding = await self._generate_embeddings_raw([text])
            self._embedding_cache[cache_key] = (embedding[0], time.time())
            results.append(embedding[0])
    return results
```

**收益**：重复/相似查询（如"总结今天的笔记"）命中缓存时省去 Embedding API 调用（100-300ms）  
**风险**：极低。内存占用可控（单个 embedding ~4KB，1000 条约 4MB）

### 2.4 路由分数未用于跳过不必要的 RAG

**现状**：[`app/rag/rag_service.py:257-285`](../app/rag/vector_store.py#L257-L285)

`compute_route_score()` 已实现，通过查询向量与知识库 Top-1 的 L2 距离判断是否需要 RAG。但 **chat.py 中从未调用此方法**，每次请求都无条件执行完整 RAG 管线。

#### 方案：RAG 前先做路由判断（快速路径）

在 `chat.py` 的 RAG 阶段，先用 `compute_route_score()` 快速判断查询与知识库的相关性：

- 若 L2 距离 > `RAG_ROUTE_THRESHOLD`（默认 0.5），说明查询与知识库无关（如"你好"、"今天天气怎么样"），**跳过 RAG 管线**
- 若 L2 距离 ≤ 阈值，执行完整 RAG 管线

**注意**：`compute_route_score()` 本身也需要一次 Embedding + ChromaDB 查询，但这个查询只取 Top-1，比完整管线（双源检索 + 重排序 + 总结）轻量得多。

**收益**：与知识库无关的查询省去 90% 的 RAG 耗时  
**风险**：路由判断本身约 100-200ms，对相关查询是额外开销。需权衡路由判断的成本与跳过 RAG 的收益

### 2.5 RagService 每次请求重建

**现状**：[`app/routers/chat.py:112-118`](../app/routers/chat.py#L112-L118)

每次请求都 `VectorStoreService()` + `RagService()` 创建新实例。虽然 `VectorStoreService` 是单例（`__new__` 双重检查），但 `RagService` 每次都重建。

#### 方案：RagService 由 init_manager 统一管理

在 `main.py` 的 `BackgroundInitManager` 阶段 2 中创建 `RagService` 实例并挂载，路由层直接引用 `init_manager.rag_service`。

**收益**：减少对象创建开销（约 1-5ms）  
**风险**：极低

## 三、瓶颈 2：LLM API 连接池 / Keep-Alive 复用

### 3.1 ChatOpenAI 没有配置连接池（预估节省 100-300ms）

**现状**：[`app/utils/factory.py:121-126`](../app/utils/factory.py#L121-L126)

```python
ChatOpenAI(
    model=model_name,
    api_key=api_key,
    base_url=DASHSCOPE_BASE_URL,
    streaming=True,
    # ❌ 没有 http_client / http_async_client
    # ❌ 没有 request_timeout
)
```

底层 `httpx` 虽然有自己的默认连接池，但未显式配置：
- `max_keepalive_connections` 默认较小（通常 10）
- `keepalive_expiry` 默认较短
- 没有超时配置，流式请求可能无限挂起

#### 方案：创建模块级共享 httpx AsyncClient

```python
# 改造思路（不修改代码，仅示意）
import httpx

# 模块级共享的异步 HTTP 客户端（在 factory.py 模块顶层创建）
_async_http_client: httpx.AsyncClient | None = None

def _get_async_http_client() -> httpx.AsyncClient:
    global _async_http_client
    if _async_http_client is None or _async_http_client.is_closed:
        _async_http_client = httpx.AsyncClient(
            timeout=httpx.Timeout(
                timeout=120.0,     # 总超时（流式响应需要较长）
                connect=5.0,       # 连接超时
            ),
            limits=httpx.Limits(
                max_keepalive_connections=20,   # 保持 20 个空闲连接
                max_connections=100,            # 最大 100 个并发连接
                keepalive_expiry=60,            # 空闲连接 60 秒后回收
            ),
            transport=httpx.AsyncHTTPTransport(retries=1),
        )
    return _async_http_client

# 传入 ChatOpenAI
ChatOpenAI(
    model=model_name,
    api_key=api_key,
    base_url=DASHSCOPE_BASE_URL,
    streaming=True,
    http_async_client=_get_async_http_client(),  # ✅ 复用连接
    request_timeout=120.0,                        # ✅ 超时保护
)
```

**收益**：
- TCP/TLS 握手消除：首次请求后的后续请求节省 50-150ms
- Keep-Alive 复用：同一连接可发送多个请求，减少网络往返
- 超时保护：避免流式请求无限挂起

**风险**：
- `httpx.AsyncClient` 需要在应用关闭时正确释放（在 `lifespan` 的 shutdown 阶段调用 `await client.aclose()`）
- LangChain 的 `ChatOpenAI` 可能内部也会管理 `http_async_client` 的生命周期，需验证

### 3.2 Embedding 模型与 Chat 模型共享连接池

当前 Chat 模型和 Embedding 模型都访问同一个 DashScope 端点（`https://dashscope.aliyuncs.com/compatible-mode/v1`），但各自使用独立的 HTTP 客户端。应**共享同一个连接池**，最大化连接复用效率。

#### 方案：统一的 HTTP 客户端管理

```python
# 改造思路（不修改代码，仅示意）
# 在 factory.py 模块中统一管理
_shared_async_client: httpx.AsyncClient | None = None
_shared_sync_client: httpx.Client | None = None

def get_async_http_client() -> httpx.AsyncClient:
    """获取共享的异步 HTTP 客户端（Chat + Embedding 共用）"""
    ...

def get_sync_http_client() -> httpx.Client:
    """获取共享的同步 HTTP 客户端（Embedding 同步调用时使用）"""
    ...
```

**收益**：减少连接数，提高连接复用率  
**风险**：需在应用关闭时统一清理

## 四、补充优化

### 4.1 RAG 检索与记忆压缩并行执行（预估节省 50-200ms）

**现状**：[`app/routers/chat.py:102-250`](../app/routers/chat.py#L102-L250)

RAG 检索（步骤 4）和记忆压缩（步骤 6）串行执行，但两者**无数据依赖关系**。

#### 方案：并行执行

```python
# 改造思路（不修改代码，仅示意）
async def run_rag():
    return await rag_service.query(...)

async def run_compression():
    return compress_messages(...)

# 并行执行
rag_result, compressed = await asyncio.gather(
    run_rag(),
    run_compression(),
)
```

**收益**：总延迟 = max(RAG耗时, 压缩耗时)，而非两者之和。预估节省 50-200ms  
**风险**：RAG 失败时压缩已执行（浪费少量资源），需处理异常隔离

---

### 4.2 数据库查询合并

**现状**：[`app/routers/chat.py:193-195`](../app/routers/chat.py#L193-L195)

记忆压缩阶段分别执行 `get_all_messages()` 和 `get_summary()`，两次独立的 DB 查询。

#### 方案：合并为一次查询 或 并行执行

- 方案 A：将两条查询用 `asyncio.gather` 并行执行
- 方案 B：用一次 JOIN 查询同时获取消息和摘要

**收益**：减少一次 DB 往返（约 5-20ms）  
**风险**：低

### 4.3 Agent 图结构缓存

**现状**：[`app/ai_service/agent_runner.py:58`](../app/ai_service/agent_runner.py#L58)

每次请求调用 `create_agent()` 编译 LangGraph StateGraph，有一定开销。

#### 方案：缓存编译好的 Agent 图

对于相同 `system_prompt` + `tools` 组合，缓存编译结果。

**注意**：当前 Agent 实例化开销不大（10-50ms），且不同用户/会话的 system_prompt 可能因 RAG 上下文而不同，缓存命中率有限。优先级较低。

---

### 4.4 token_budget 配置对象缓存

**现状**：[`app/routers/chat.py:176-185`](../app/routers/chat.py#L176-L185)

每次请求从 YAML 文件读取配置并创建 `TokenBudget` 对象。

#### 方案：模块加载时缓存配置

`get_token_budget_config()` 结果在模块加载时缓存（当前已有 `load_yaml` 但无跨请求缓存）。

**收益**：微小（约 1-5ms）  
**风险**：无

## 八、风险与注意事项

1. **httpx AsyncClient 生命周期管理**：必须在应用关闭时正确 `aclose()`，否则可能导致连接泄漏。在 `lifespan` shutdown 阶段处理。

2. **文档总结移除后的上下文质量**：轻量截断可能使上下文不如 LLM 总结精准。建议通过 `RAG_ENABLE_SUMMARIZE` 开关保留回退能力，上线后监控回答质量。

3. **路由判断误判风险**：`RAG_ROUTE_THRESHOLD=0.5` 默认值需根据实际使用数据调优。阈值过低会漏掉相关查询，过高则跳不过无关查询。建议收集日志后调整。

4. **Embedding 缓存的时效性**：如果知识库频繁更新，缓存的 Embedding 与新文档的相似度匹配可能不准。查询 Embedding 本身不变，缓存安全。

5. **DashScope 兼容性**：DashScope Embedding SDK 的 HTTP 客户端配置方式可能与标准 OpenAI SDK 不同，需查阅 `langchain_community.embeddings.DashScopeEmbeddings` 源码确认。

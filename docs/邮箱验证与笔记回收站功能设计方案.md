## 2. 邮箱发送功能

### 2.1 注册邮箱验证

#### 2.1.1 流程设计

```
用户输入邮箱 → 点击"发送验证码" → 后端生成6位验证码
    → 存入 Redis（key: email_code:{email}, TTL: 5min）
    → QQ SMTP 发送邮件 → 用户输入验证码 → 提交注册
    → 后端校验验证码 → 验证通过 → 创建用户（email_verified=True）
```

#### 2.1.2 配置项（`.env` 文件新增）

```env
# ========== QQ 邮箱 SMTP 配置 ==========
SMTP_HOST=smtp.qq.com
SMTP_PORT=587
SMTP_USERNAME=your_qq_email@qq.com
SMTP_PASSWORD=your_qq_smtp_authorization_code   # QQ邮箱授权码，非登录密码
SMTP_FROM_NAME=云上笔记
```

> **注意**：QQ 邮箱 SMTP 密码不是 QQ 登录密码，需要在 QQ 邮箱 `设置 → 账户 → POP3/SMTP 服务` 中开启并获取授权码。

#### 2.1.3 新增依赖

```txt
# requirements.txt 新增
aiosmtplib>=3.0.0         # 异步 SMTP 客户端
```

#### 2.1.4 后端模块设计

**新建文件：`app/services/email_service.py`**

```
EmailService
├── __init__(self, config: dict)        # 从环境变量加载 SMTP 配置
├── send_email(to, subject, body,       # 核心发送方法（异步 SMTP + 重试）
│             retries=2, backoff=2.0)    # 最多重试 2 次，指数退避（2s → 4s）
├── send_verification_code(to)          # 发送验证码（封装模板 + 重试）
├── generate_code() -> str              # 生成 6 位数字验证码
└── verify_code(email, code) -> bool    # 校验验证码（查询 Redis）
```

**重试策略**：

```python
async def send_email(self, to, subject, body, retries=2, backoff=2.0):
    """发送邮件，自动重试瞬态错误"""
    last_error = None
    for attempt in range(retries + 1):
        try:
            async with aiosmtplib.SMTP(...) as smtp:
                await smtp.send_message(msg)
            return  # 成功
        except (aiosmtplib.SMTPConnectError, aiosmtplib.SMTPTimeoutError) as e:
            last_error = e
            if attempt < retries:
                await asyncio.sleep(backoff * (2 ** attempt))
        except aiosmtplib.SMTPAuthenticationError:
            raise  # 认证错误不重试（配置问题）
    raise last_error  # 重试耗尽
```

> **注意**：`send-code` 端点调用 `send_verification_code` 时，若最终仍失败，应返回友好提示"发送失败，请稍后重试"，而非让用户看到 SMTP 异常堆栈。

**关键实现细节**：

1. **验证码存储**：Redis key 格式 `email_code:{email}`，value 为验证码，TTL 300 秒（5 分钟）
2. **发送频率限制**：同一邮箱 60 秒内只能发送一次（Redis key `email_code_cooldown:{email}`）
3. **验证码邮件模板**：HTML 格式，存放在 `templates/email/verification_code.html`，包含应用名称、验证码、有效期提示。`EmailService` 通过文件路径加载，避免 HTML 硬编码在 Python 代码中
4. **验证码校验**：从 Redis 查询 → 比对 → 删除 Redis 记录（一次性使用）

### 2.2 AI 对话中笔记转 Markdown 发送邮箱

#### 2.2.1 场景描述

用户在 AI 对话界面选中笔记，要求 AI 将笔记以 Markdown 格式发送到邮箱。

#### 2.2.2 邮箱获取策略（两级降级）

**⚠️ 关键前提**：当前 `get_user_info_tools` 仅返回 `"当前用户 ID: {user_id}"`（见 [agent_tools.py:57-59](../app/ai_service/agent_tools.py#L57-L59)），**不包含 email 字段**。必须先行扩展该工具，否则 LLM 无法获取用户邮箱。

**扩展 `get_user_info_tools`**：在 `create_agent_tools` 工厂函数中预查询用户信息并存入闭包，避免 Agent 重复调用工具时反复查询数据库：

```python
def create_agent_tools(user_id, ..., db_session_factory=None, ...):
    # ★ 延迟缓存：始终初始化，避免 db_session_factory 为 None 时 nonlocal 报错
    from app.models.user import User
    from sqlalchemy import select
    _user_cache = {"fetched": False, "user": None}

    @tool
    async def get_user_info_tools() -> str:
        """获取当前登录用户的基本信息（用户名、邮箱）"""
        nonlocal _user_cache
        if not _user_cache["fetched"]:
            if db_session_factory:
                async with db_session_factory() as db:
                    result = await db.execute(select(User).where(User.uuid == user_id))
                    _user_cache["user"] = result.scalar_one_or_none()
            _user_cache["fetched"] = True

        user = _user_cache["user"]
        if user:
            email_info = user.email if user.email else "未设置邮箱"
            return f"用户名: {user.username}\n邮箱: {email_info}\n用户ID: {user_id}"
        return f"当前用户 ID: {user_id}（用户信息获取失败）"
```

> **设计说明**：采用延迟初始化模式（首次调用时查询，后续命中缓存）。`_user_cache` 始终在 `@tool` 定义前初始化，避免 `db_session_factory` 为 `None` 时 `nonlocal` 引用未定义变量的 `NameError`。

**两级降级策略**：

```
1. LLM 调用 get_user_info_tools → 获取 email 字段
   ├─ email 非空 → 确认后发送：'即将把笔记发送至您的邮箱 {email}，确认发送吗？'
   └─ email 为空（"未设置邮箱"）→ 降级到步骤 2
2. LLM 在对话中询问用户输入目标邮箱地址
3. 若用户未提供 → 返回提示"请先提供目标邮箱地址或在个人设置中绑定邮箱"
```

#### 2.2.3 `send_email` 工具改造

修改 [app/ai_service/agent_tools.py:235-247](../app/ai_service/agent_tools.py#L235-L247) 的占位实现。

> **注意**：当前 `send_email` 仅为普通 `async def` 函数，缺少 `@tool` 装饰器。改造时需两步：① 加 `@tool` 装饰器使其成为 LangChain Tool 对象；② 替换模拟返回为真实 SMTP 调用。`email_service` 实例通过闭包捕获（完整注入链路见 2.2.4 节），此处代码与 2.2.4 节保持一致：

```python
@tool
async def send_email(to: str, subject: str, body: str) -> str:
    """
    发送邮件。将笔记内容以 Markdown 格式发送到指定邮箱。
    ...
    """
    if not email_service:
        return "邮件服务未初始化，请联系管理员"
    try:
        await email_service.send_email(to, subject, body)
        return f"笔记已成功发送至 {to}"
    except Exception as e:
        logger.error(f"邮件发送失败: to={to}, error={e}")
        return f"邮件发送失败：{e}。请检查邮箱地址是否正确，或稍后重试。"
```

> **注意**：捕获所有异常并返回友好提示，防止 SMTP 异常（连接超时、认证失败、重试耗尽等）直接冒泡到 Agent 框架导致 Agent 循环中断。

**将 `send_email` 注册到工具表**：在 `agent_tools.py` 的 `all_tools` 字典中添加：

```python
all_tools = {

}
```

**在 `config/agent.yaml` 中注册工具组和路由规则**（见 [config/agent.yaml:74-91](../config/agent.yaml#L74-L91)）：

```yaml

# tool_routing.keyword_rules 新增
```

### 5.2 限流策略

> **⚠️ 当前限流模块限制**：`app/core/rate_limit.py` 的 `rate_limit()` 只接受 `global_limit` 和 `endpoint_limit`（单位：**次/分钟**），**不支持自定义窗口时长**。`RATE_LIMIT_WINDOW = 60` 是硬编码常量。因此"每 IP N次/小时"的限流**不能通过 `rate_limit` 装饰器实现**，需采用手动 Redis 计数器。

**方案**：小时级限流在端点逻辑内手动实现（Redis key 按小时分桶），分钟级限流复用 `rate_limit` 装饰器。

| 端点 | 策略 | 实现方式 |
|------|------|---------|
| `POST /auth/send-code` | 每邮箱 1次/60秒 | `EmailService` 内检查 Redis key `email_code_cooldown:{email}` |
| `POST /auth/send-code` | 每 IP 10次/小时 | 端点内手动 Redis 计数器（key: `send_code_ip:{ip}:{hour}`，TTL 3600s） |
| `POST /auth/register` | 每 IP 5次/分钟 | 已有 `/api/v1/auth` 的 `ENDPOINT_RATE_LIMITS` 中配置为 5，直接复用 |
| `DELETE /note/{id}/permanent` | 每用户 30次/分钟 | 新增 Redis 计数器（key: `perm_delete:{user_id}`，TTL 60s），在端点内手动实现 |

> **注意**：`ENDPOINT_RATE_LIMITS` 字典中 `/api/v1/auth: 5` 会通过前缀匹配覆盖 `/api/v1/auth/send-code`，导致 send-code 被限为 5次/分钟。需在 `ENDPOINT_RATE_LIMITS` 中新增更长的前缀条目 `/api/v1/auth/send-code`，利用最长前缀匹配规则覆盖默认值：

```python
ENDPOINT_RATE_LIMITS = {
    # ... 现有条目 ...
    "/api/v1/auth/send-code": 10,   # ★ 新增：更长前缀 → 优先匹配 → 覆盖 /api/v1/auth:5
    "/api/v1/auth": 5,
}
```

**IP 小时级限流实现**（在 `POST /auth/send-code` 端点内手动实现，不通过 `rate_limit` 装饰器）：

```python
# app/routers/user.py — send_code 端点
from fastapi import Request
from app.db.redis_client import get_redis
from datetime import datetime

@router.post("/auth/send-code")
async def send_code(data: SendCodeRequest, request: Request):
    redis = get_redis()

    # 1. 邮箱冷却检查（60s）
    cooldown_key = f"email_code_cooldown:{data.email}"
    if await redis.exists(cooldown_key):
        ttl = await redis.ttl(cooldown_key)
        raise BusinessError(code=ErrorCode.ENDPOINT_RATE_LIMIT,
            message=f"发送过于频繁，请 {ttl} 秒后再试")

    # 2. IP 小时级限流（10次/小时）
    client_ip = (
        request.headers.get("X-Forwarded-For", "").split(",")[0].strip()
        or request.headers.get("X-Real-IP", "").strip()
    )
    if not client_ip:
        client_ip = request.client.host if request.client else None
    if not client_ip:
        # 无法获取 IP → 跳过 IP 限流，仅依赖邮箱维度限流
        logger.warning(f"send-code: 无法获取客户端 IP，跳过 IP 限流")
    else:
        hour_bucket = datetime.now().strftime("%Y%m%d%H")
        ip_key = f"send_code_ip:{client_ip}:{hour_bucket}"
        ip_count = await redis.incr(ip_key)
        if ip_count == 1:
            await redis.expire(ip_key, 3600)
        if ip_count > 10:
            raise BusinessError(code=ErrorCode.ENDPOINT_RATE_LIMIT,
                message="请求过于频繁，请稍后再试")

    # 3. 生成验证码 + 发送邮件（略）
    ...
```

## 7. 定时任务设计

### 7.1 清理过期笔记

**逻辑**：每天凌晨 3:00 执行，从 MySQL 物理删除 `deleted_at < NOW() - 14天` 的记录，同时清理 ChromaDB 向量。

### 7.2 实现方案：APScheduler

**新增依赖**：

```txt
apscheduler>=3.10.0        # 定时任务调度
```

**新建文件：`app/core/scheduler.py`**

```python
"""
定时任务调度器

使用 APScheduler 管理周期性后台任务：
- 每天凌晨 3:00 清理过期笔记（deleted_at > 14 天）
- 每天凌晨 4:00 清理过期验证码（Redis 已有 TTL，备用兜底）
"""

from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger

scheduler = AsyncIOScheduler()

async def cleanup_expired_notes():
    """清理过期笔记（deleted_at 超过 14 天）

    运行在请求上下文之外，需自行获取数据库和向量存储实例：
    - DB session：通过 `from app.db.database import async_session_factory` 获取独立会话
    - VectorStore：通过 `from main import init_manager` → `init_manager.note_service.vector_store`
    """

    from app.db.database import async_session_factory
    from app.models.note import Note
    from sqlalchemy import select, delete, and_
    from datetime import datetime, timedelta
    from main import init_manager

    cutoff = datetime.now() - timedelta(days=14)
    vector_store = init_manager.note_service.vector_store if init_manager.note_service else None

    async with async_session_factory() as db:
        # 1. 查询过期笔记 ID 列表
        result = await db.execute(
            select(Note.id).where(
                and_(Note.deleted_at.isnot(None), Note.deleted_at < cutoff)
            )
        )
        expired_ids = [row[0] for row in result.fetchall()]

        if not expired_ids:
            logger.debug("无过期笔记需要清理")
            return 0

        # 2. 从 ChromaDB 批量删除对应向量
        if vector_store:
            for note_id in expired_ids:
                try:
                    await vector_store.delete_note_vectors(note_id)
                except Exception as e:
                    logger.warning(f"清理过期向量失败: note_id={note_id}, error={e}")
            # ★ 效率说明：当前采用逐条删除，每次触发一次 ChromaDB 查询。
            # 若过期笔记量很大（>1000 条），可考虑在 VectorStoreService 中新增
            # batch_delete_note_vectors(note_ids: List[str]) 方法，使用
            # collection.delete(where={"note_id": {"$in": note_ids}}) 一次性批量删除。

        # 3. 从 MySQL 物理删除记录（级联删除 review_records）
        del_result = await db.execute(
            delete(Note).where(Note.id.in_(expired_ids))
        )
        await db.commit()

        logger.info(f"清理过期笔记完成: 删除 {del_result.rowcount} 条")
        return del_result.rowcount

def init_scheduler():
    """初始化并启动定时任务"""
    scheduler.add_job(
        cleanup_expired_notes,
        trigger=CronTrigger(hour=3, minute=0),
        id="cleanup_expired_notes",
        name="清理过期笔记",
        replace_existing=True,
    )
    scheduler.start()
```

**集成到应用生命周期**：在 [main.py](../main.py) 的 `lifespan` 中加入 scheduler 的启停逻辑：

```python
# lifespan 启动阶段（yield 之前）
if not reload:
    init_scheduler()
    logger.info("定时任务调度器已启动")
else:
    logger.info("检测到 reload 模式，跳过 scheduler 启动（避免重复执行）")

yield

# lifespan 关闭阶段（yield 之后）
if not reload:
    scheduler.shutdown(wait=False)   # wait=False 避免阻塞关闭流程
    logger.info("定时任务调度器已关闭")
```

> `wait=False` 参数确保 scheduler 关闭时不阻塞 FastAPI 的 shutdown 流程。若 scheduler 正在执行某次清理任务，该任务会被中断，下次启动后重新调度。

**⚠️ 关键：防止 uvicorn reload 模式下的重复执行**

项目默认 `reload=True`（见 [main.py:366](../main.py#L366)），reload 模式下 uvicorn 会 fork 子进程，导致父子进程各启动一个 scheduler，同一清理任务每天执行两次。

防护策略（三选一，推荐方案 A）：

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **A. 环境变量检测** | 仅在非 reload 模式下启动 scheduler | 简单可靠，推荐 |
| B. 文件锁（`filelock`） | 执行前获取锁，未获取到则跳过 | 需要额外依赖 |
| C. APScheduler `Event` | 通过 Redis pub/sub 选举 leader | 分布式友好但复杂 |

**方案 A 实现**：

```python
# main.py lifespan 启动阶段
import os
reload = os.getenv("UVICORN_RELOAD", "true").lower() not in ("false", "0", "no")
if not reload:
    init_scheduler()
    logger.info("定时任务调度器已启动")
else:
    logger.info("检测到 reload 模式，跳过 scheduler 启动（避免重复执行）")
```

### 7.3 备用方案：asyncio 轻量实现

若不希望引入 APScheduler 依赖，可使用 `asyncio.create_task` + 每日循环：

```python
async def daily_cleanup_loop():
    while True:
        now = datetime.now()
        # 计算距离凌晨 3:00 的秒数
        target = now.replace(hour=3, minute=0, second=0, microsecond=0)
        if target <= now:
            target += timedelta(days=1)
        await asyncio.sleep((target - now).total_seconds())
        await cleanup_expired_notes()
```

推荐使用 APScheduler，功能更完善、可观测性更好。

## 8. 安全与风控

### 8.1 邮箱验证码安全

| 措施 | 说明 |
|------|------|
| 验证码有效期 | 5 分钟（Redis TTL） |
| 一次性使用 | 验证成功后立即删除 Redis 记录 |
| 发送频率限制 | 同一邮箱 60 秒内仅发送 1 次 |
| IP 频率限制 | 同一 IP 每小时最多发送 10 次 |
| 验证码位数 | 6 位纯数字（100 万种组合） |
| 防暴力破解 | 同一邮箱验证码错误 5 次后锁定 15 分钟 |

### 8.2 回收站安全

| 措施 | 说明 |
|------|------|
| 权限校验 | 所有操作校验 `user_id` 归属 |
| 双确认 | 彻底删除需经过确认弹窗 |
| 恢复校验 | 只能恢复 `deleted_at IS NOT NULL` 的笔记 |

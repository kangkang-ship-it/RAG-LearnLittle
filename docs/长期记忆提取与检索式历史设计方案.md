## 一、动机与时机

### 1.1 短期方案的极限

滑动窗口 + 摘要压缩方案在处理以下场景时会遇到瓶颈：

| 场景 | 问题 |
|------|------|
| 用户在第300轮提到"我之前说过我喜欢简洁回答"，但摘要未涵盖 | 偏好丢失，助手回答风格偏离 |
| 跨会话引用："上次对话中我们讨论过的那个方案" | 摘要会话隔离，无法跨会话 |
| 对话间断（用户隔了2周再回来），窗口内没有足够上下文 | 窗口全是新消息，旧背景丢失 |
| 摘要质量波动：某次摘要 LLM 遗漏了关键决策 | 信息永久丢失，无法溯源 |

### 1.2 长期记忆方案的优势

```
短期方案（窗口+摘要）:
  历史 → 时间线性 → 窗口截断 → 旧信息被压缩或丢弃

长期记忆方案（提取+检索）:
  历史 → 提取关键事实 → 向量化存储 → 语义检索 → 相关记忆注入
                    ↑
              跨会话、跨时间、按相关性
```

### 1.3 建议的触发时机

| 指标 | 阈值 | 说明 |
|------|------|------|
| 单会话消息数 | > 200 条 | 窗口 + 摘要开始吃力 |
| 用户总会话数 | > 10 个 | 跨会话上下文有价值 |
| 用户活跃天数 | > 30 天 | 长期偏好和事实积累足够 |
| 摘要遗漏投诉 | ≥ 3 次 | 用户反馈助手"忘了"重要信息 |

## 三、记忆类型模型

### 3.1 记忆分类

不同类型的记忆在提取、存储和使用上有不同的处理策略：

```
┌──────────────┬──────────────────────┬────────────────────┬──────────────┐
│    类型       │        示例           │      存储字段        │   优先级      │
├──────────────┼──────────────────────┼────────────────────┼──────────────┤
│ preference   │ "用户喜欢简洁回答"      │ preference_*        │ 高（每次注入）│
│ (偏好)       │ "用户是Python开发者"    │                     │              │
├──────────────┼──────────────────────┼────────────────────┼──────────────┤
│ decision     │ "决定使用FastAPI框架"   │ decision_*          │ 高（关键决策）│
│ (决策)       │ "数据库选MySQL+Redis"  │                     │              │
├──────────────┼──────────────────────┼────────────────────┼──────────────┤
│ fact         │ "用户的笔记有300篇"     │ fact_*              │ 中（按需检索）│
│ (事实)       │ "项目截止日期是周五"    │                     │              │
├──────────────┼──────────────────────┼────────────────────┼──────────────┤
│ context      │ "最近在研究RAG技术"     │ context_*           │ 中（按需检索）│
│ (上下文)     │ "当前项目涉及3个服务"   │                     │              │
├──────────────┼──────────────────────┼────────────────────┼──────────────┤
│ action       │ "答应帮用户整理笔记"    │ action_*            │ 高（未完成时）│
│ (待办/承诺)  │ "下次对话提醒用户..."   │                     │              │
└──────────────┴──────────────────────┴────────────────────┴──────────────┘
```

### 3.2 记忆 Schema

```python
# 文件位置: app/models/user_memory.py (新增)

from datetime import datetime
from typing import Optional
from sqlalchemy import String, Text, DateTime, Integer, Float, JSON, ForeignKey, func, Enum as SAEnum
from sqlalchemy.orm import Mapped, mapped_column, relationship
from app.models.base import Base
import enum


class MemoryType(str, enum.Enum):
    """记忆类型枚举"""
    PREFERENCE = "preference"   # 用户偏好
    DECISION = "decision"       # 关键决策
    FACT = "fact"               # 事实信息
    CONTEXT = "context"         # 上下文/状态
    ACTION = "action"           # 待办/承诺


class MemoryStatus(str, enum.Enum):
    """记忆状态"""
    ACTIVE = "active"           # 活跃（正常检索使用）
    ARCHIVED = "archived"       # 已归档（不再检索）
    SUPERSEDED = "superseded"   # 被更新的记忆取代
    COMPLETED = "completed"     # 待办已完成


class UserMemory(Base):
    """
    用户长期记忆模型

    从对话中提取的关键事实、偏好、决策等信息片段。
    每条记忆都经过向量化存储在 ChromaDB 中，支持语义检索。

    记忆生命周期：
    ACTIVE → SUPERSEDED (被新记忆覆盖)
    ACTIVE → COMPLETED (待办完成)
    ACTIVE → ARCHIVED   (人工归档)
    """
    __tablename__ = "user_memories"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)

    # 所属用户
    user_id: Mapped[str] = mapped_column(
        String(36), ForeignKey("users.uuid", ondelete="CASCADE"),
        nullable=False, index=True
    )

    # 记忆类型
    memory_type: Mapped[MemoryType] = mapped_column(
        SAEnum(MemoryType), nullable=False, default=MemoryType.FACT
    )

    # 记忆内容（人类可读的一句话摘要）
    content: Mapped[str] = mapped_column(Text, nullable=False)

    # 详细上下文（原始对话片段，用于溯源）
    context: Mapped[str | None] = mapped_column(Text, nullable=True)

    # 重要性评分 (0.0 ~ 1.0)
    importance: Mapped[float] = mapped_column(Float, nullable=False, default=0.5)

    # 状态
    status: Mapped[MemoryStatus] = mapped_column(
        SAEnum(MemoryStatus), nullable=False, default=MemoryStatus.ACTIVE
    )

    # 来源信息
    source_session_id: Mapped[str | None] = mapped_column(
        String(36), nullable=True, index=True
    )
    source_message_id: Mapped[int | None] = mapped_column(
        Integer, nullable=True
    )

    # 去重键（基于标准化文本的 hash，防止重复提取）
    dedup_key: Mapped[str] = mapped_column(
        String(64), nullable=False, unique=True, index=True
    )

    # ChromaDB 中的对应向量 ID
    vector_id: Mapped[str | None] = mapped_column(
        String(64), nullable=True
    )

    # 过期时间（可选，偏好类记忆可设长期有效）
    expires_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)

    # 被取代时指向新的记忆 ID
    superseded_by: Mapped[int | None] = mapped_column(
        Integer, ForeignKey("user_memories.id"), nullable=True
    )

    # 时间戳
    created_at: Mapped[datetime] = mapped_column(
        DateTime, server_default=func.now(), nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime, server_default=func.now(), onupdate=func.now(), nullable=False
    )

    # ========== 关联关系 ==========
    user = relationship("User")
```

### 4.3 去重策略

```python
# 文件位置: app/services/memory_extractor.py (新增)

import hashlib
from typing import List

class MemoryDeduplicator:
    """
    记忆去重器

    三层去重策略：
    1. 标准化文本 hash 去重（精确匹配）
    2. 同类记忆语义相似度比对（向量相似度 > 0.9 视为重复）
    3. 冲突检测：新记忆与已有记忆矛盾时，标记旧记忆为 SUPERSEDED
    """

    @staticmethod
    def compute_dedup_key(user_id: str, content: str) -> str:
        """计算去重键"""
        # 标准化：去除多余空格、统一标点
        normalized = " ".join(content.lower().split())
        hash_input = f"{user_id}:{normalized}"
        return hashlib.sha256(hash_input.encode()).hexdigest()

    async def check_duplicate(
        self,
        user_id: str,
        content: str,
        memory_type: str,
        db: AsyncSession,
    ) -> bool:
        """
        检查是否与已有记忆重复

        1. 精确去重：相同 dedup_key
        2. 语义去重：同类型记忆中向量相似度 > 0.9
        """
        dedup_key = self.compute_dedup_key(user_id, content)

        # Level 1: 精确去重
        from sqlalchemy import select
        result = await db.execute(
            select(UserMemory).where(UserMemory.dedup_key == dedup_key)
        )
        if result.scalar_one_or_none():
            return True

        # Level 2: 语义去重（向量相似度）
        vector_store = get_user_memory_vector_store()
        similar = await vector_store.search_by_text(
            text=content,
            user_id=user_id,
            filter_type=memory_type,
            k=3,
        )
        for mem in similar:
            if mem.get("score", 0) > 0.9:
                return True

        return False

    async def detect_conflict(
        self,
        new_memory: dict,
        existing_memories: list[UserMemory],
    ) -> list[UserMemory]:
        """
        检测新记忆是否与已有记忆冲突

        示例：
        已有: "用户使用 PostgreSQL"
        新提取: "用户决定从 PostgreSQL 迁移到 MySQL"
        → 旧记忆标记为 SUPERSEDED，指向新记忆
        """
        conflicts = []

        for old in existing_memories:
            if old.memory_type != new_memory["type"]:
                continue

            # 使用 LLM 判断是否构成冲突/更新
            is_conflict = await self._llm_check_conflict(
                old.content, new_memory["content"]
            )
            if is_conflict:
                conflicts.append(old)

        return conflicts
```

## 五、记忆检索与注入

### 5.1 检索策略

```
MemoryRetriever.retrieve(query, user_id, k=5)

检索流程:
┌─────────────────────────────────────────────────────────┐
│  1. 预处理 query                                         │
│     ├── 生成检索变体（原 query + 关键实体替换 + 意图概括） │
│     └── 如有最近对话上下文，追加检索词                    │
│                                                         │
│  2. 向量检索（ChromaDB）                                  │
│     ├── 对 query 变体分别编码                            │
│     ├── 在 user_memories collection 中检索               │
│     ├── 按 max(scores) 去重合并结果                       │
│     └── 返回 top-10 候选                                 │

│     ├── 按 (向量相似度 * 0.6 + importance * 0.4) 加权    │
│     ├── Preference 类型记忆 +0.1 加权                     │
│     ├── 未完成的 Action 类型记忆 +0.2 加权                │
│     └── 返回 top-5                                       │
│                                                         │
```

### 5.2 注入格式

```python
# 文件位置: app/services/memory_retriever.py

def format_memories_for_prompt(memories: list[UserMemory]) -> str:
    """
    将检索到的记忆格式化为 prompt 可用的文本

    不同类型的记忆使用不同的前缀和格式，
    方便 LLM 理解其语义角色。
    """
    if not memories:
        return ""

    lines = ["## 用户长期记忆\n"]

    # 按类型分组展示
    grouped: dict[str, list[UserMemory]] = {}
    for m in memories:
        grouped.setdefault(m.memory_type.value, []).append(m)

    type_labels = {
        "preference": "🎯 用户偏好",
        "decision": "📋 关键决策",
        "fact": "📌 已知事实",
        "context": "🔄 当前上下文",
        "action": "⏳ 待办事项",
    }

    for mem_type, mems in grouped.items():
        label = type_labels.get(mem_type, mem_type)
        lines.append(f"### {label}")
        for m in mems:
            importance_bar = "█" * int(m.importance * 5) + "░" * (5 - int(m.importance * 5))
            lines.append(f"- {m.content}  [{importance_bar}]")
        lines.append("")

    return "\n".join(lines)
```

```python
async def _trigger_memory_extraction(context: dict) -> None:
    """

    在 _trigger_summary_check 之后执行。
```

```python
async def assemble_context(
    session_id: str,
    user_id: str,
    query: str,
    db: AsyncSession,
) -> list[BaseMessage]:
    """
    Phase 2 共存期：整合短期 + 长期记忆
    """
    messages = []

    # 1. System prompt
    messages.append(SystemMessage(content=system_prompt))

    # 2. RAG 上下文（现有）
    if rag_context:
        messages.append(SystemMessage(content=f"## 知识库检索结果\n{rag_context}"))

    # 3. 长期记忆（新增）
    retriever = MemoryRetriever()
    memories = await retriever.retrieve(query, user_id, k=5)
    if memories:
        memory_text = format_memories_for_prompt(memories)
        messages.append(SystemMessage(content=memory_text))

    # 4. 对话摘要（短期方案）
    summary = await session_manager.get_summary(db, session_id)
    if summary:
        messages.append(SystemMessage(
            content=f"[历史对话摘要]\n{summary}"
        ))

    # 5. 滑动窗口（短期方案）
    history = await session_manager.get_messages(db, session_id, user_id)
    compressor = MemoryCompressor(budget, TokenCounter())
    window_messages, _ = compressor.build_context(
        all_messages=history,
        existing_summary="",  # 摘要已单独注入
    )
    messages.extend(window_messages)

    # 6. 当前问题
    messages.append(HumanMessage(content=query))

    return messages
```

## 九、性能与成本估算

### 9.1 存储成本估算

```
假设:
- 活跃用户: 1000 人
- 每用户日均对话轮数: 20 轮
- 每轮提取记忆数: 1 条（平均）
- 每条记忆 MySQL 存储: ~1KB

日新增记忆数: 1000 × 20 × 1 = 20,000 条
日新增 MySQL 存储: 20,000 × 1KB = 20MB
月新增 MySQL 存储: 20MB × 30 = 600MB
年新增 MySQL 存储: ~7GB

ChromaDB 向量存储:
- 每条记忆向量维度: 1536 (text-embedding-3-small)
- 每条向量存储: 1536 × 4 bytes ≈ 6KB
- 月新增: 20,000 × 30 × 6KB ≈ 3.6GB
- 年新增: ~43GB

总计（年）: MySQL ~7GB + ChromaDB ~43GB ≈ 50GB / 1000用户
```

### 9.2 LLM 调用成本

```
记忆提取 LLM 调用:
- Prompt: ~500 tokens (系统prompt + 对话内容)
- Response: ~200 tokens (JSON 格式记忆列表)
- 每轮消耗: ~700 tokens
- 每用户日消耗: 20 × 700 = 14,000 tokens
- 每千用户日消耗: 14M tokens

记忆检索 Embedding:
- 每请求: 1次 query embedding (1536维) + top-5 回查
- 每千用户日请求: 20,000 次
- embedding API 日消耗: 20,000 × ~20 tokens ≈ 0.4M tokens

总计（每千用户每日）: ~14.4M tokens
```

### 9.3 延迟影响

```
写入链路（异步，不阻塞响应）:
  记忆提取 LLM 调用: 1-3 秒（后台异步执行）

读取链路（同步，影响响应延迟）:
  query embedding: ~50ms
  ChromaDB 检索: ~20ms
  MySQL 回查: ~10ms
  总延迟增量: ~80ms（用户可接受）
```

## 十、风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|:----:|---------|
| **记忆提取质量低**：LLM 提取出噪音或无意义内容 | 中 | `importance` 评分阈值过滤（< 0.5 不检索）；用户可手动删除/修正记忆 |
| **隐私泄露**：敏感信息被提取为记忆 | 高 | 记忆仅存储在当前用户空间；提供"清除长期记忆"功能；敏感检测（身份证、密码等跳过提取） |
| **记忆膨胀**：随时间积累过多低价值记忆 | 中 | 自动归档：30天未被检索 + importance < 0.3 → ARCHIVED；定期触发 LLM 记忆清理 |
| **检索噪音**：不相关的记忆注入 prompt，干扰 LLM 判断 | 中 | 向量相似度阈值（< 0.5 不注入）；限制注入数量（max 5 条）；LLM 被告知"如果相关则参考，否则忽略" |
| **LLM 上下文污染**：长期记忆占比过大，挤占其他组件空间 | 低 | 长期记忆 token 上限：`LONG_TERM_MEMORY_MAX_TOKENS = 1000`；超出时按 importance 截断 |
| **提取 LLM 调用失败**：成本问题或 API 不可用 | 低 | 异步提取，失败不影响主流程；降级到仅使用短期方案；监控失败率告警 |
